# 智能文旅策划助手：行程规划优化方案

**日期：** 2026-08-28  
**状态：** 需求规格，待实现评审  
**范围：** 行程规划输入、知识库融合、方案制定与历史方案编辑

## 一、优化目标

将当前“填写固定表单并生成一次性结果”的流程，调整为“自然语言提出需求 → 大模型提取约束 → 知识库与多 Agent 协同规划 → 保存方案 → AI 交互修改”的闭环。

优化后用户不需要理解系统字段，只需完整描述旅行需求。系统仍使用结构化数据合同和现有多 Agent 编排，确保日期、人数、地点和偏好可验证、可追踪、可持续编辑。

## 二、范围与明确约束

### 2.1 包含内容

- 行程规划页改为自然语言需求输入；
- 大模型提取始发地、目的地、日期、人数、天数、预算和偏好；
- 缺少必填信息时弹窗提示并阻止规划；
- 将知识库 RAG 融入路线规划链路；
- 新增“方案制定”导航窗口，选择并编辑已保存方案；
- 通过 AI 客服对已保存方案提出修改要求；
- 修改后更新当前方案、查询记录和版本信息。

### 2.2 不包含内容

- 不执行购票、订房、支付或其他外部交易；
- 不删除文档库管理能力，文档库仍用于知识内容维护；
- 不保留独立的“攻略查询”用户入口；
- 不允许模型未经校验直接写入路线事实或覆盖用户明确约束。

## 三、信息架构调整

侧边导航调整为：

```text
行程规划
方案制定
门票查询
酒店推荐
数据看板
文档库
```

删除“攻略查询”导航按钮及其独立视图、地区搜索框和查询结果面板。知识检索接口和文档库继续保留，但只由行程规划服务内部调用。

“方案制定”用于查看已保存的旅行规划方案。用户可按最近修改时间选择方案，进入方案详情和 AI 修改区。

## 四、自然语言输入与信息提取

### 4.1 用户输入

规划页提供一个多行文本框，允许用户一次描述全部需求，例如：

> 两位成人带一个孩子，9 月 10 日从上海去成都玩 5 天，不吃辣，想安排自然景点，节奏不要太赶。

提交时将原始 query 原样发送到后端。前端不再通过逗号拆分偏好，也不承担语义解析职责。

### 4.2 大模型提取合同

大模型输出严格受控的结构化结果，至少包括：

```json
{
  "origin": "上海",
  "destination": "成都",
  "departure_date": "2026-09-10",
  "travelers": 3,
  "days": 5,
  "budget": null,
  "preferences": ["携带儿童", "不吃辣", "自然景点", "节奏不要太赶"],
  "missing_fields": [],
  "ambiguous_fields": []
}
```

提取结果必须经过服务端 Pydantic 合同校验。模型不能确定的字段视为缺失或歧义，不得自行猜测。始发地、目的地、出行日期、出行人数、出行天数为必填项；预算和偏好为可选项。

### 4.3 缺失字段交互

当 `missing_fields` 或 `ambiguous_fields` 包含必填字段时：

1. 不调用路线、天气、住宿或餐饮 Agent；
2. 弹出明确提示，例如“出行日期是必填项”“目的地信息不明确，请补充具体城市或景区”；
3. 保留用户原始 query，允许补充后重新提取；
4. 多个字段缺失时一次性列出全部字段，避免用户反复提交。

模型调用失败、输出无法解析或合同校验失败时，使用统一错误提示，不将模型原始响应展示给用户。

## 五、RAG 与多 Agent 融合

### 5.1 规划链路

```text
原始 query
  → 大模型信息提取与歧义识别
  → 必填项校验
  → 目的地/日期/人群/偏好知识检索
  → 天气 Agent
  → 路线 Agent（接收 RAG 上下文与天气约束）
  → 住宿 Agent
  → 餐饮 Agent
  → 汇总 Agent
  → 保存 TravelPlan 方案并返回
```

### 5.2 知识命中规则

- 命中相关文档时，将检索片段、来源、版本和更新时间作为受控上下文传给路线及汇总 Agent；
- 仅采纳与当前目的地、日期、人群和偏好匹配的内容；
- 知识库内容是规划依据，不是无条件事实。营业时间、天气、路线耗时等时效信息仍以实时服务或核验提示为准；
- 知识库部分命中时，采用“知识库内容 + 实时 Agent 结果”合并生成；
- 完全未命中时，继续执行多 Agent 链路生成完整路线和旅游攻略，并在结果中标注暂无相关知识库内容；
- RAG 文本一律视为数据，不执行其中包含的指令；
- 保留来源、知识库版本和降级状态，沿用现有 `TravelPlanDocument` 的可追溯输出边界。

### 5.3 偏好约束

偏好必须进入结构化请求和 Agent 上下文，而不是只用于生成说明文字：

- 饮食禁忌传给餐饮 Agent，用于过滤候选和生成替代建议；
- 儿童、老人等同行人群传给路线、住宿和餐饮 Agent，影响景点强度、时长、交通和设施筛选；
- 节奏、兴趣、交通方式、无障碍等偏好应形成可审计约束；
- 若实时数据与偏好冲突，结果必须说明冲突并给出可核验替代方案，不得静默忽略偏好。

## 六、方案制定与保存

### 6.1 方案记录

每次成功或降级生成的方案都应形成可保存记录，至少包含：

- `plan_id`、原始 query、结构化请求快照；
- 当前 `TravelPlanDocument`；
- 创建时间、更新时间和当前版本号；
- 来源、警告、降级 Agent 和修改状态；
- 修改历史及每次修改的用户指令。

查询记录展示方案标题、目的地、日期、状态和最近修改时间。记录中的方案内容必须来自服务端保存结果，不能只依赖前端内存状态。

### 6.2 方案制定页面

页面由三部分组成：

1. 已保存方案列表；
2. 当前方案详情，展示路线、攻略、来源和待核验事项；
3. AI 客服交互区，用于提出修改要求。

示例修改请求包括“把第二天安排得轻松一些”“不吃辣的餐厅全部替换”“增加适合儿童的室内景点”。

## 七、AI 修改与记录同步

### 7.1 修改流程

```text
选择已保存方案
  → 用户输入修改要求
  → AI 读取当前方案、原始约束和修改历史
  → 提取修改意图与受影响字段
  → 重新检索知识库并调用必要 Agent
  → 规则校验与偏好校验
  → 生成新版本方案
  → 原子更新方案记录与查询记录
```

AI 修改不能只替换 Markdown 文本。必须更新结构化 `itinerary`，再由汇总 Agent 生成 Markdown 表现层，确保后续修改仍以结构化事实为准。

### 7.2 版本与并发

- 每次修改生成递增版本号，保留上一版本以便审计和恢复；
- 更新使用版本条件校验，避免多个窗口覆盖彼此的修改；
- 修改失败、校验失败或外部服务不可用时，不覆盖当前有效版本；
- 查询记录与方案详情必须在同一服务端事务或等价原子操作中更新；
- 前端更新成功后刷新当前方案、列表摘要和更新时间，避免旧内容残留。

## 八、错误处理与安全边界

- 必填字段缺失：业务弹窗，状态为“待补充”，不进入 Agent；
- 大模型提取失败：提示重新描述或补充字段，不展示 Prompt 和原始响应；
- RAG 无结果：降级为多 Agent 规划，并明确标注知识库未命中；
- 单个 Agent 失败：沿用现有 `failed`/`degraded` 结果信封，其余 Agent 可继续；
- 修改后结构化合同不通过：拒绝提交新版本并保留旧版本；
- 所有用户输入、知识片段和模型输出均进行长度限制、敏感信息控制和 Markdown 安全净化；
- AI 客服只修改旅行方案，不执行预订、支付和对外发送等动作。

## 九、接口与模块影响

建议新增或扩展以下服务边界：

- `POST /api/travel-plans/parse`：自然语言 query 提取结构化请求；
- `POST /api/travel-plans`：接收提取结果及 RAG 上下文，生成并保存方案；
- `GET /api/travel-plans`、`GET /api/travel-plans/{plan_id}`：方案列表和详情；
- `POST /api/travel-plans/{plan_id}/revisions`：提交 AI 修改并生成新版本；
- `GET /api/travel-plans/{plan_id}/revisions`：查看修改历史；
- 现有文档库、知识检索和外部服务接口继续作为内部依赖，不再直接绑定独立攻略页面。

接口命名和具体字段应在实现计划中与现有 API 风格、请求追踪标识及错误合同统一。

## 十、验收标准

- 用户只填写自然语言即可触发行程规划；
- 五个必填字段缺失或歧义时均能弹窗准确提示，且不会启动 Agent；
- 同义表达和组合语义可被正确提取；
- “不吃辣”“携带儿童”等偏好能影响对应 Agent 的结果；
- 知识库命中内容能够被引用并与实时规划合并，未命中时能够由多 Agent 完整生成；
- 前端不再出现“攻略查询”导航和独立查询窗口，文档库仍可管理；
- 生成方案可在“方案制定”中保存、选择和查看；
- AI 修改后结构化行程、Markdown、列表摘要、查询记录和版本号保持一致；
- 修改失败不会破坏原方案，历史版本可追溯；
- 现有来源、警告、降级和安全渲染测试不回退。

## 十一、实施顺序建议

1. 定义自然语言提取合同、必填字段和模型失败错误合同；
2. 将 RAG 检索接入行程规划编排，补充来源和未命中状态；
3. 调整前端行程规划输入并移除攻略查询导航与视图；
4. 建立服务端方案记录、版本和查询记录同步能力；
5. 新增“方案制定”页面及 AI 修改接口；
6. 补充单元、接口契约、RAG 回归、偏好约束和前端 E2E 测试。
