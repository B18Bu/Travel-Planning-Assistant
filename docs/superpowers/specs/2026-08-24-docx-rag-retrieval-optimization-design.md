# DOCX 结构化分块与检索优化设计

**日期：** 2026-08-24  
**状态：** 已实现并通过后端测试  
**范围：** 仅优化既有文档库 RAG 中 DOCX 的结构提取、结构感知分块、混合检索候选数量和文档范围过滤；不改变旅行规划链路、前端布局、嵌入模型或 Chroma 存储边界。

---

## 1. 目标与边界

### 1.1 目标

提升完整旅游设计方案 DOCX 的可检索性和来源可理解性：

1. 标题层级、正文、表格和图表 OCR 文本在入库时保留原始文档顺序和所属标题路径；
2. 正文以章节语义和自然边界分块，而不是将每个段落独立按字符滑窗切分；
3. 表格块携带章节路径、表格序号、表头和行键值对，避免单纯单元格拼接造成语义丢失；
4. 混合检索在语义与关键词两路各召回 36 条候选，RRF 融合、去重、范围过滤后最终返回最多 12 条；
5. 指定 `document_ids` 检索时，语义与关键词两路均只能检索指定且 `ready` 的文档；
6. 空白查询在进入检索前被拒绝；
7. 单张图 OCR 不可用时，DOCX 正文和表格仍可继续入库、标记为 `ready`。

### 1.2 非目标

本次不实现或调整以下事项：

- 不增加 reranker、外部 embedding、生成式问答或 LLM 总结；
- 不改变现有 BGE 模型、Chroma collection、RRF 算法或关键词评分规则；
- 不增加 PDF/MinerU/OCR 识别能力；
- 不新增上传格式、权限、多租户、任务队列或索引重建 UI；
- 不修改出行规划、天气、路线、住宿、餐饮和既有前端页面布局。

## 2. 当前问题与根因

| 问题 | 当前行为 | 影响 |
| --- | --- | --- |
| 正文被逐段处理 | 每个段落被独立切分，标题仅存于 `source_section` 元数据 | 查询命中某段时缺少标题、地点、对象或上文约束；短段产生过多弱语义块 |
| 字符硬切 | 单项内容以 800 字符和 100 字符重叠滑窗切分 | 可在句中截断，且同章节相邻段落不会组合为完整语义单元 |
| 表格语义不足 | 表格行以单元格文本拼接 | 缺少章节、表头和键值关系，完整旅游方案中的行程、预算、交通表难以匹配查询 |
| 候选过少 | 两路候选各取 15 条，最终仅取 5 条 | 对信息完整、章节较多的旅游方案，相关块可能在融合前被截断 |
| 指定文档范围不一致 | 语义检索过滤 `document_ids`，关键词检索未传递该范围 | 指定文档搜索可混入其他文档的关键词命中 |
| 空白查询可通过 | 查询只满足非空长度约束 | 无意义查询会进入嵌入和关键词检索流程 |

## 3. DOCX 结构化提取

### 3.1 统一内容项

DOCX 解析器仍按 `document.element.body.iterchildren()` 的原始顺序遍历顶层段落和表格，但每个输出内容项必须补充以下结构信息：

```python
{
    "content_type": "text" | "table" | "chart_ocr",
    "text": "用于后续分块和向量化的受控文本",
    "section_path": ["第一章 项目概况", "1.2 客源分析"],
    "source_section": "第一章 项目概况 > 1.2 客源分析",
    "table_index": 1 | None,
    "chart_index": 1 | None,
    "source_order": 0,
}
```

- 标题样式以既有 `Heading*` 或 `标题*` 识别；标题层级由样式名中的数字推断。
- 新标题到来时，截断同级及更深层级标题，并更新对应层级；未识别标题层级时，将其作为下一层标题。
- 无标题前的正文使用 `正文` 作为唯一标题路径。
- 非空正文、表格和图片/OCR 结果均递增 `source_order`，以保证后续分块、详情和来源展示保序。
- 本次不扩展到文本框、页眉页脚、脚注、批注或 Office 原生图表对象；这些对象不应导致正文或表格处理失败。

### 3.2 正文标准化

正文项保存去除首尾空白后的原文。分块阶段为保证独立可理解性，每个正文块的实际可嵌入文本统一以下缀格式组成：

```text
章节：第一章 项目概况 > 1.2 客源分析

<该块正文>
```

- `章节：` 前缀只在存在非默认标题路径时写入；默认 `正文` 不追加该前缀。
- 不生成或复制标题本身以外的推测性摘要。
- `DocumentChunk.source_section` 保留相同的 ` > ` 拼接路径，供详情和 API 来源展示。

### 3.3 表格标准化

每个表格按原始行列顺序生成独立候选内容项，不与相邻正文合并。格式为：

```text
章节：第三章 产品设计 > 3.1 三日游线路
表格 2
表头：日期 | 行程 | 交通 | 住宿
第 1 行：日期=第一天；行程=抵达成都，宽窄巷子；交通=接机；住宿=春熙路酒店
第 2 行：日期=第二天；行程=都江堰、青城山；交通=旅游巴士；住宿=春熙路酒店
```

规则：

- 表头取首个非空行；若整个表格只有一行，则该行作为 `表头`，不生成行键值对；
- 每个后续行按列序生成 `表头=单元格值`；缺失表头使用 `第 N 列`；缺失单元格保留为空字符串；
- 表格序号在单个 DOCX 内从 1 开始递增；
- 章节路径和表格序号写入 `DocumentChunk` 来源元数据；
- 本次不推断表格标题、合并单元格的视觉布局或嵌套表格含义。

### 3.4 图片与 OCR

继续提取既有可识别的 DOCX 嵌入图片。OCR 成功时，`chart_ocr` 内容项沿用当前位置的标题路径与 `chart_index`；OCR 失败、未配置或遇到不支持的图片类型时，仅跳过该图，不影响正文、表格和其他图片入库。处理记录保留受控降级摘要，禁止暴露绝对路径、密钥、供应商原始响应或堆栈。

## 4. 结构感知分块

### 4.1 常量与块类型

- `DocumentChunk.content` 最大长度继续为 **800 个 Unicode 字符**；
- 正文块之间保留最多 **100 个字符**的尾部重叠；
- `chunk_type` 仍限制为 `text`、`table`、`chart_ocr`；
- 每块保留稳定 `chunk_id`、`document_id`、`source_section`、`table_index`、`chart_index`、`char_start` 和 `char_end`。

### 4.2 正文聚合和切分

正文只与**相同 `section_path` 且在文档顺序中连续**的正文项聚合；表格和图表 OCR 是边界，不得跨越聚合。

1. 将同章节连续正文以双换行连接，建立聚合文本及其在该聚合内容中的字符偏移；
2. 计算 `章节：...\n\n` 前缀长度后，按剩余内容空间切分正文；
3. 优先在段落末尾切分；段落无法容纳时，优先在 `。！？；` 后切分；仍无可用边界时才按字符长度切分；
4. 下一个正文块复制前一块正文部分末尾最多 100 字符，标题前缀不计入重叠；
5. 每块 `char_start` / `char_end` 指向聚合正文中的实际正文范围，不包含标题前缀；
6. 若标题路径前缀本身占满块容量，截断标题路径至可容纳范围并保留末级标题；不得生成空正文块。

这保证同章节中相邻短段落可作为完整语义片段被检索，同时不跨越表格、图表和章节边界。

### 4.3 表格分块

表格块不使用正文字符滑窗：

1. 每个表格块必须包含章节行、表格编号行和完整表头行；
2. 按完整行组累积，直到加入下一行会超过 800 字符；
3. 若存在后续行组，每个后续块重复章节、表格编号和表头；
4. 单个超长行以字符边界拆分，但每个子块仍重复章节、表格编号、表头和 `第 N 行（续）` 标记；
5. 不在两个不同表格之间合并；不使用 100 字符滑窗重叠。

### 4.4 图表 OCR 分块

`chart_ocr` 块保留章节前缀和 `图表 N` 标记；OCR 文本超过 800 字符时，可按自然句子边界切分并保留最多 100 字符正文重叠。图表 OCR 不与正文或表格合并。

## 5. 检索与 API 行为

### 5.1 检索数量

以最终 Top-K 为唯一配置源：

```python
KNOWLEDGE_SEARCH_RESULT_LIMIT = 12
KNOWLEDGE_SEARCH_FETCH_MULTIPLIER = 3
```

请求处理器计算：

```python
result_limit = settings.knowledge_search_result_limit  # 默认 12
fetch_limit = result_limit * 3                         # 默认 36
```

- Chroma 语义检索召回 `fetch_limit` 条；
- 关键词检索召回 `fetch_limit` 条；
- 两路按现有 RRF 合并、按当前规则去重和排序；
- API 最多返回 `result_limit` 条；不足时返回实际命中数；
- 不能仅修改 `ChromaStore.query` 的默认参数，因为 API 必须显式传入统一的 `fetch_limit`。

配置字段应使用既有 `Settings` 和环境变量加载方式。默认值为 **12**；配置值必须是大于 0 的整数。为控制 API 响应体和前端渲染成本，上限为 **50**，超出上限应在配置加载时产生明确的受控配置错误。

### 5.2 文档范围过滤

`POST /api/knowledge-search` 在生成 `ready_ids` 后，将 `payload.document_ids` 同时传入：

```python
chroma_store.query(query, document_ids=payload.document_ids, limit=fetch_limit)
search_chunks(ready_chunks, parsed_query, limit=fetch_limit, document_ids=payload.document_ids)
```

`ready_chunks` 必须只来自 `ready_ids`。关键词检索内部使用同样的 `document_ids` 范围；语义结果、关键词结果和最终融合结果中的每个 `document_id` 都必须属于该集合。没有指定 `document_ids` 时，范围为全部 `ready` 文档。

### 5.3 查询标准化

检索入口在 Pydantic 解析后的第一步执行 `query = payload.query.strip()`：

- 结果为空时返回现有 API 的 422 请求校验错误；
- 非空时，将标准化后的 `query` 同时传给语义检索和 `parse_query`；
- 不改变已存在的最大长度限制。

## 6. 错误处理与兼容性

- DOCX 解析失败、BGE 编码失败或 Chroma 写入失败：保留既有 `failed` 状态和向量清理行为；
- 单图 OCR 异常、未配置或不支持图片类型：仅记录受控降级信息，正文/表格处理继续；
- 空正文、空表格或空 OCR 文本：不生成空块、不调用 embedding；
- 已有 `documents.json` 中历史分块保持可读；只有重新上传或重新处理的 DOCX 使用新分块格式；本次不做存量数据迁移；
- 文档详情、分块 API 和知识检索 API 保持已有响应字段，新增或填充的 `source_section` / `table_index` 不应破坏前端对未知字段的兼容。

## 7. 测试与验收

### 7.1 单元测试

`backend/tests/test_document_extractors.py`：

1. 三层标题和多个短正文段落解析后产生正确 `section_path` 和 `source_section`；
2. 同章节连续短段落聚合为包含标题前缀的正文块，表格前后正文不跨表格合并；
3. 超长正文优先在段落和句子边界切分，只有无边界时按字符切分，且相邻正文块正文部分重叠最多 100 字符；
4. 每个表格块包含章节、表格编号、表头和行键值对；多块表格重复表头；
5. 超长单行表格拆分时保留 `第 N 行（续）`、章节、表格编号和表头；
6. OCR 图表块继承当前位置标题路径；单图 OCR 失败不会删除正文和表格项。

`backend/tests/test_keyword_search.py`：

1. `document_ids` 过滤后，关键词候选只包含指定文档；
2. 关键词与语义结果合并后，范围外候选无法通过 RRF 返回；
3. `limit=36` 时仍按现有 RRF 规则稳定排序并去重。

`backend/tests/test_config.py`：

1. 未设置环境变量时检索结果上限为 12；
2. 合法正整数环境变量可覆盖默认值；
3. 0、负数、非整数和大于 50 的配置被拒绝。

### 7.2 API 回归测试

`backend/tests/test_documents_api.py`：

1. 语义与关键词各收到 `fetch_limit=36`，最终响应最多 12 条；
2. 当所有候选少于 12 时按实际数量返回；
3. 指定 `document_ids` 时，关键词命中范围外文档也不得出现在响应中；
4. 仅由空白组成的 `query` 返回 422，且不会调用 Chroma 或关键词检索；
5. 未指定文档范围时仍可检索所有 `ready` 文档；
6. 所有返回块保留文档名、类型、分数和来源字段，且不包含绝对路径、密钥或供应商原始异常。

### 7.3 验收标准

1. 包含标题、短正文段落和行程表的 DOCX 入库后，命中片段可从 `source_section` 看出所属方案章节；
2. 查询表格中的日期、景点、交通或住宿时，返回片段同时含表头和对应行键值；
3. 完整旅游方案的相关章节多于 5 个时，API 可返回最多 12 个经融合排序的来源片段；
4. 指定一份文档检索时，任何检索模式均不会返回其他文档的块；
5. 单张图 OCR 不可用时，正文和表格仍可以 `ready` 状态检索；
6. 现有文档上传、状态流转、Chroma `ready` 过滤、旅行规划 API 和前端资产测试继续通过。
