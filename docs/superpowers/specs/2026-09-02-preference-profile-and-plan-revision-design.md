# 用户偏好画像与已保存方案修订设计

## 目标

让自然语言中的同行人群与饮食偏好成为可执行约束，而不是仅出现在提示词中；同时将方案修订改为用户明确选中一条已保存方案后，再由 AI 按自定义描述生成新版本。

## 范围与非范围

- 范围：偏好解析、结构化画像、路线与餐饮约束、最终合规校验、修订选择流程、已保存方案删除、相关接口与测试。
- 非范围：重新设计整个工作台、保证未标注商家的清真或食材事实、修改既有完整测试中已过期的日期夹具。

## 偏好画像

新增 `TravelPreferenceProfile`，由大模型根据 `original_query` 生成受控 JSON。画像包含同行人群、任意数量的偏好项、优先级、禁止项、待确认项，以及按路线、餐饮、住宿和摘要分组的指导；不以固定的老人、儿童、清真或饮食词表作为主要理解方式。

每个偏好项包含 `category`、`priority`、`instruction`、`exclude_terms` 与 `verification_required`。这使“摄影友好、少排队、素食、轮椅友好”等未预设偏好也可以传入后续 Agent。

代码只校验模型 JSON 的结构、长度和受控优先级，并对模型产生的 `exclude_terms` 做通用候选文本过滤；不对具体偏好作词表判断。模型不可用或输出不合法时保留原始描述并标记“偏好理解暂不可用”，不得臆测画像。画像加入 `TravelPlanRequest`，编排器沿用同一个请求对象传递给天气、路线、住宿、餐饮和摘要 Agent。

## 约束执行

### 路线

- 根据模型的路线指导调整每日密度、候选排序和活动说明；例如模型表达“老人同行、节奏舒缓”时减少主要时段，表达“亲子互动优先”时提升相应候选。
- 不将任何特定人群规则写死；路线 Agent 同时保留原始画像，供其生成说明与后续模型能力使用。

### 餐饮

- 使用模型画像每个 `must` 偏好的 `exclude_terms` 对名称、菜系、标签和特色字段做通用文本过滤。
- 需核验的偏好不将未知候选描述为已满足，而是带上模型产生的确认事项。
- 餐饮 Agent 不维护“不吃辣、清真”等业务词表。

### 住宿、天气与摘要

- 住宿和天气仅输出可由已有资料支持的建议，不虚构无障碍、亲子设施或清真餐厅事实。
- 摘要列出已响应约束、已排除的明确冲突以及待向商家确认的事项。
- 编排器在生成文档前执行最终合规检查，移除所有违反明确饮食硬约束的候选。

## 已保存方案修订

方案制定页增加“修改已保存方案”入口。打开一个带两步进度的同一弹窗：

1. 拉取已保存方案，按路线、天数、创建时间和当前版本展示；用户必须单选一条方案。
2. 展示所选方案概要，用户输入本次修改描述；仅当已选择方案且描述非空时允许提交。

提交调用 `POST /api/travel-plans/saved/{plan_id}/revisions`。服务端以所选方案的原始需求与新的修改描述重新解析并规划，生成递增版本；不会修改未被选择的方案。

成功后刷新该方案版本并在当前工作台展示结果。关闭结果弹窗只移除遮罩，不调用视图切换或导航逻辑，因此保留当前工作台、滚动位置和表单状态。对 404、409、422、网络错误分别显示中文可恢复提示，并保留输入内容供重试。

## 已保存方案删除

增加 `DELETE /api/travel-plans/saved/{plan_id}` 与存储层删除方法。删除按钮只针对已保存方案，显示方案名称/路线的二次确认；成功后刷新列表并显示结果，失败时不从界面预先移除该项。

## 可访问性与交互

- 两步弹窗展示当前步骤；所有控件使用原生可聚焦元素、可见焦点样式和符合视觉顺序的键盘顺序。
- 异步提交期间禁用重复提交并显示加载状态；字段错误就近显示，弹窗关闭按钮始终可用。
- 删除使用文字标签或 `aria-label`，并提供二次确认；关闭弹窗后焦点返回触发按钮。

## 测试与验收

新增单元和接口测试，覆盖：模型画像解析与传递、未预设偏好的保留、模型失败时不臆测偏好、模型 `exclude_terms` 的通用过滤、待确认提示、最终合规校验、修订版本递增、删除、404/409/422 异常处理。前端测试或浏览器验证覆盖：选择方案后才能进入描述步骤、输入为空不可提交、成功后停留工作台、关闭弹窗不出现白屏、键盘操作与加载反馈。

完整后端套件中既有的过期日期和本机环境覆盖失败不纳入本次修复；本次交付以新增及关联测试全部通过为准，并记录完整套件的既有失败。
