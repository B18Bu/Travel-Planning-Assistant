# 顺序编排式文旅多 Agent 改造设计

**日期：** 2026-08-18  
**状态：** 已确认，待进入实现计划  
**适用范围：** 智能文旅策划助手首期企业化改造

---

## 1. 背景与目标

当前项目以单一大模型生成完整旅行方案，并用 RAG 知识库补充目的地攻略。首期改造将原有「路程规划、美食推荐、住宿建议、天气建议」的单次 API 生成模式替换为顺序编排的专业 Agent 协作模式。

目标是让每类结论由受控的专业 Agent 基于外部数据与自有知识库产生，再由汇总 Agent 进行一致性校验和文档编制，避免单一模型凭空生成实时事实。

### 1.1 首期目标

- 根据用户问题依次调用天气、路线、住宿、美食 4 个专业 Agent。
- 使用和风天气、高德地图及已审核知识库作为事实来源。
- 由汇总与校验 Agent 生成可阅读、可追溯、可降级的完整文旅策划文档。
- 每个外部数据结论均展示来源、数据类型和更新时间。
- 外部服务失败时仍尽可能返回最小可用建议，不伪造实时信息。

### 1.2 非目标

首期不建设或不允许以下能力：

- 未经授权的 OTA、点评平台数据抓取。
- 实时房价、剩余房量、订单可订状态、餐饮排队时长、实时优惠等无授权数据。
- 未经用户二次确认的预订、支付、退改、投诉或营销触达。
- 由 Agent 绕过服务端权限直接访问密钥、数据库或外部服务。
- 用模型推断伪装成实时交通、天气、价格或库存事实。

## 2. 用户输入与默认规则

### 2.1 输入字段

| 字段 | 是否必填 | 说明 |
|---|---:|---|
| 出发地 | 是 | 用于往返路线、交通方式与通行时间估算。 |
| 目的地 | 是 | 用于天气、地理编码、POI、知识库检索及行程安排。 |
| 出行日期 | 是 | 用于天气预报、预警判断和行程日期排布。 |
| 人数 | 是 | 用于住宿房型建议、餐饮适配及预算分摊。 |
| 旅行天数 | 否 | 不填写时默认 `3 天 2 晚`。 |
| 预算 | 否 | 用于经济/舒适/品质层级筛选；未填写时不输出精确预算承诺。 |
| 偏好 | 否 | 例如亲子、银发、文化体验、自然风光、饮食偏好、无障碍需求。 |

### 2.2 默认策略

- 未填写旅行天数：默认按 **3 天 2 晚** 规划，并在文档中明确说明可以调整。
- 未填写预算：酒店和餐饮仅输出定位、便利性、适配人群与品质层级建议，不承诺价格与库存。
- 地名不明确：编排器先使用高德地理编码标准化；无法确定时要求用户补充，而不随意猜测。

## 3. 总体架构与顺序编排

```text
用户表单 / 自然语言问题
    │
    ▼
需求标准化与编排器
字段校验、地名标准化、request_id、超时和调用预算
    │
    ▼
① 实时天气与气候预测 Agent
和风天气 API + 气候知识库
    │ 天气风险、活动约束
    ▼
② 旅游路线规划 Agent
高德地图 API + 路线/景区知识库
    │ 每日活动区域、路线与时间锚点
    ▼
③ 旅店测评 Agent
高德 POI + 已审核住宿知识库
    │ 住宿区域与候选建议
    ▼
④ 美食品鉴 Agent
高德 POI + 已审核餐饮知识库
    │ 每日餐饮建议
    ▼
⑤ 汇总与校验 Agent
规则引擎 + 结构化结果 + 文档模板
    │
    ▼
完整文旅策划文档（Markdown / 后续支持 PDF）
来源、更新时间、风险提示、降级说明
```

### 3.1 编排原则

1. 天气 Agent 必须先运行。出现暴雨、台风、高温、强对流等预警时，天气约束必须传递给路线 Agent。
2. 路线 Agent 是住宿与餐饮 Agent 的空间锚点，必须输出每日活动区域、起止时间和 POI 上下文。
3. 酒店与餐饮 Agent 仅基于高德 POI、已授权公开信息和已审核知识库回答，不能声明无授权实时字段。
4. 汇总 Agent 只能使用前序 Agent 的结构化结果和已有来源；不得擅自补充未验证事实。
5. 编排器负责超时、重试、缓存、熔断、降级和审计；专业 Agent 不直接管理密钥或执行外部写操作。

## 4. Agent 职责与数据边界

### 4.1 实时天气与气候预测 Agent

| 项目 | 设计 |
|---|---|
| 输入 | 目的地、出行日期、旅行天数。 |
| 外部数据 | 和风天气 API。 |
| 内部知识 | 气候常态、季节性出游建议、风险处置知识库。 |
| 输出 | 每日天气、气温、降雨/预警、活动适宜度、穿衣与装备建议、风险等级、更新时间。 |
| 约束 | 不将预报表达为绝对安全结论；预警必须明确展示。 |
| 下游约束 | 例如「首日上午避免长时间户外活动」「高温时段安排室内展馆」。 |

### 4.2 旅游路线规划 Agent

| 项目 | 设计 |
|---|---|
| 输入 | 出发地、目的地、日期、人数、天数、预算、天气约束。 |
| 外部数据 | 高德地图地理编码、路径规划、距离、POI 等服务。 |
| 内部知识 | 景区开放规则、预约须知、区域路线知识库。 |
| 输出 | 往返建议、每日活动区域、POI 顺序、预计时长、路线风险、来源与更新时间。 |
| 约束 | 不伪造实时车票、票价、余票或预约名额；路径建议需受天气约束。 |
| 下游约束 | 每日住宿区域、就餐区域、时间窗口和交通可达性。 |

### 4.3 旅店测评 Agent

| 项目 | 设计 |
|---|---|
| 输入 | 人数、住宿晚数、每日路线节点、预算层级、偏好。 |
| 外部数据 | 高德 POI。 |
| 内部知识 | 已审核住宿知识库，包括设施、适配人群、位置说明和服务标签。 |
| 输出 | 推荐住宿区域、候选住宿 POI、通勤便利性、设施标签、适合人群、推荐理由、来源和更新时间。 |
| 约束 | 不提供实时房价、库存、可订状态或未经授权的平台评分。 |
| 降级 | 无候选时输出住宿区域、筛选条件和官方/平台查询入口。 |

### 4.4 美食品鉴 Agent

| 项目 | 设计 |
|---|---|
| 输入 | 每日活动区域、就餐时间、人数、预算层级、饮食偏好。 |
| 外部数据 | 高德 POI。 |
| 内部知识 | 已审核餐饮知识库，包括菜系、特色、适合人群和饮食提醒。 |
| 输出 | 每日餐饮建议、菜系/特色、位置、营业时间（有来源时）、适合人数、来源与更新时间。 |
| 约束 | 不提供排队时长、实时优惠、未经授权评分等字段。 |
| 降级 | 无候选时输出餐饮区域、菜系方向、筛选建议和查询入口。 |

### 4.5 汇总与校验 Agent

| 项目 | 设计 |
|---|---|
| 输入 | 前 4 个 Agent 的结构化结果及执行状态。 |
| 外部数据 | 无直接外部事实查询权限。 |
| 内部能力 | 规则引擎、冲突校验、模板渲染、来源合并和安全审核。 |
| 输出 | 最终行程文档、每日安排、风险提示、冲突说明、来源与更新时间、降级说明。 |
| 约束 | 不新增前序证据以外的事实；存在冲突时优先实时预警、官方规则和实时路线数据。 |

## 5. 统一 Agent 返回合同

所有专业 Agent 必须返回结构化 JSON，不直接将自然语言段落交给下游。

```json
{
  "agent": "weather",
  "status": "success",
  "summary": "出行首日有小雨，建议将主要户外活动调整至第 2 天。",
  "data": {},
  "constraints": [
    "第 1 天上午避免长时间户外活动"
  ],
  "sources": [
    {
      "name": "和风天气",
      "type": "weather_api",
      "updated_at": "2026-08-18T10:00:00+08:00",
      "url": "https://..."
    }
  ],
  "warnings": [],
  "degraded": false,
  "request_id": "...",
  "trace_id": "..."
}
```

### 5.1 状态定义

| 状态 | 含义 | 编排器处理 |
|---|---|---|
| `success` | 已获得完整、有效结果。 | 正常传递给下游。 |
| `partial` | 获得部分有效结果。 | 传递可用字段，并将缺失项写入文档。 |
| `degraded` | 外部数据不可用，已使用合法降级路径。 | 传递降级结果，并明确标注非实时/待核验。 |
| `failed` | 无可用结果。 | 按规则跳过、转人工或输出最小可用方案。 |

---

## 6. 运行状态机与降级策略

### 6.1 状态机

```text
RECEIVED
  → VALIDATING
  → WEATHER_RUNNING
  → ROUTE_RUNNING
  → LODGING_RUNNING
  → FOOD_RUNNING
  → VALIDATING_RESULT
  → SUMMARIZING
  → COMPLETED

异常分支：
  → DEGRADED（可继续）
  → ESCALATED（需人工或提示用户）
  → FAILED（无法生成最小可用方案）
```

### 6.2 降级规则

| 异常场景 | 系统行为 |
|---|---|
| 和风天气不可用 | 路线 Agent 不使用天气约束；最终文档提示「天气数据暂不可用，请出行前再次核验」。 |
| 出现恶劣天气预警 | 优先安排室内、短距离或可调整活动；文档置顶展示风险提示，禁止绝对安全表述。 |
| 高德路线服务不可用 | 返回目的地区域化建议，不输出精确通行时间、路线顺序或拥堵结论。 |
| 高德 POI 查询失败 | 酒店/餐饮 Agent 回退至已审核知识库，并标注知识库版本和非实时属性。 |
| 酒店/餐饮无结果 | 不编造商家名；输出推荐区域、餐饮类型、筛选条件和查询入口。 |
| 单个 Agent 超时 | 结束调用、记录错误类型与 `trace_id`；将已有结果交给汇总 Agent，并声明缺失信息。 |
| 汇总校验发现冲突 | 实时预警、官方规则、实时路线数据优先；不能消解时保留冲突与替代建议。 |

## 7. 超时、重试、缓存与熔断

| 项目 | 首期规则 |
|---|---|
| 单外部 API 超时 | 连接 3 秒，读取 8 秒，总计 10 秒。 |
| 单 Agent 总超时 | 15 秒。 |
| 汇总 Agent 超时 | 20 秒。 |
| 端到端最大等待 | 60 秒。 |
| 重试 | 仅网络错误、`429`、`5xx`；最多 2 次；指数退避 + 随机抖动。 |
| 熔断 | 同一服务 1 分钟内连续失败达到阈值后，暂停调用 1—5 分钟，直接降级。 |
| 天气缓存 | 目的地 + 日期缓存 30—60 分钟；预警缩短缓存。 |
| 地理编码缓存 | 地址/城市标准化结果缓存 7 天。 |
| 路线缓存 | 起终点 + 出行方式 + 日期缓存 5—15 分钟。 |
| POI 缓存 | 基础 POI 1—24 小时；时效字段单独标注更新时间。 |

## 8. 最终文档输出规范

最终返回 Markdown，后续可基于同一结构渲染为 PDF。建议章节：

1. 行程概览：出发地、目的地、日期、人数、默认天数与预算层级。
2. 天气与出游风险：逐日天气、预警、装备和活动建议。
3. 往返与每日路线：每日活动区域、推荐 POI 顺序、时间窗口与调整建议。
4. 住宿建议：推荐区域、候选 POI、通勤便利性、设施与适配人群。
5. 美食建议：按每日区域与餐次给出菜系、特色、位置和适配说明。
6. 风险与待核验项：天气、营业、预约、价格、库存等需要用户确认的信息。
7. 来源与更新时间：按 Agent 和内容类型列出引用来源。
8. 降级说明：明确哪些数据源未能获得实时结果及替代策略。

输出禁止项：

- 没有授权数据支撑时，不输出实时房价、余房、可订状态、排队时长、实时优惠。
- 不将模型推断写成「最快」「最便宜」「必然可订」「天气安全」等绝对事实。
- 不展示任何服务端密钥、内部 URL、原始异常堆栈或敏感审计信息。

## 9. 安全、审计与合规要求

- 和风天气、高德地图等密钥仅保存在服务端 Secret Manager/环境变量；任何普通用户接口不得回显密钥。
- Agent 通过受控服务端工具访问外部 API；工具须使用明确 Schema、固定域名白名单、超时、限流和审计。
- 每次请求记录 `request_id`、`trace_id`、租户/用户标识、Agent 状态、工具调用、数据源版本、来源、更新时间与降级结论。
- 外部数据最小化传输；不得向第三方传递不必要个人信息。
- 输出需经 HTML/Markdown 安全净化；所有用户输入、POI 名称、知识库字段通过安全 DOM API 渲染。
- 首期 Agent 不拥有支付、预订、文件删除、配置修改或外部写操作的工具权限。

## 10. 首期验收标准

| 分类 | 验收标准 |
|---|---|
| 功能完整性 | 四项必填信息有效时，完成天气 → 路线 → 住宿 → 餐饮 → 汇总全链路，生成 3 天 2 晚文档。 |
| 可追溯性 | 所有天气、路线、POI 和知识库结论均带来源名称、数据类型、更新时间。 |
| 可信输出 | 不出现实时房价、余房、排队、无授权评分等禁止字段；不将推断包装为实时事实。 |
| 风险处理 | 天气预警触发后，风险提示展示率 100%；外部服务失败时有明确降级说明。 |
| 性能 | 缓存未命中 p95 端到端响应目标 ≤45 秒；缓存命中 p95 ≤12 秒。 |
| 稳定性 | 任一非关键 Agent 故障不导致整体请求失败；可按 `request_id` / `trace_id` 追溯。 |
| 安全 | 外部密钥仅由服务端读取；Agent 不执行支付、预订、爬取或未授权写操作。 |

## 11. 实施边界与后续演进

首期采用顺序、固定编排，保证可预测性和可审计性。后续在满足质量、稳定性、成本和安全评测后，再考虑引入动态规划 Agent、OTA/酒店授权接口、餐饮授权评分接口、票务预订、数字人讲解、多语言和多租户运营能力。

优先实施顺序：

1. 先完成安全、认证、密钥治理、生产部署和可观测性基线。
2. 新建统一外部数据工具层：和风天气、高德地理编码、路径规划、POI。
3. 实现 4 个专业 Agent 的结构化合同与固定顺序编排器。
4. 实现汇总校验、来源标注、降级说明和完整文档输出。
5. 建立外部 API 故障、恶劣天气、无 POI、超时、数据冲突等自动化测试。
6. 在一个目的地/景区群试点，基于质量、成本和用户反馈再扩展功能。
