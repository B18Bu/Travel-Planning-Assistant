# 自定义行程描述字段解析设计

## 目标

让自定义行程描述优先通过确定性规则提取必填字段，模型解析失败时仍能保留已识别信息；页面仅提示首个确实缺失的字段。

## 范围

- 识别“从北京到成都”形式的始发地、目的地。
- 识别无年份的 `9.10 日` 日期，并按当前最近未来日期补全年份。
- 识别“玩 3 天”形式的出行天数。
- 将成人、儿童人数相加为总出行人数。
- 保留模型对预算、偏好的补充能力。
- 缺失或不明确时，按既定字段顺序仅提示一个字段，例如“请补充出行人数”。

## 方案

`TravelQueryParser` 先以本地规则提取始发地、目的地、日期、人数与天数，再调用模型补充未被规则识别的字段与可选信息。规则已确认的字段优先于模型结果；模型响应无效或请求失败时，返回规则结果及按字段顺序计算的 `missing_fields`，不再抛出会掩盖字段状态的解析异常。

字段顺序固定为：始发地、目的地、出行日期、出行人数、出行天数。前端从 `missing_fields` 与 `ambiguous_fields` 的合并结果中取首项，展示“请补充{字段名}”或“请确认{字段名}”。

预算与偏好不属于生成行程的必填字段；“不吃辣”“行程不要太赶”应作为偏好保留，不能触发缺失提示。

## 错误处理

- 日期无法构成有效日期：标记 `departure_date` 缺失。
- 成人或儿童描述无法求出正整数：标记 `travelers` 缺失。
- 模型失败：不丢弃规则结果；仅返回规则无法确定的必填字段。
- 无任何可用解析结果且模型响应无效：返回空字段与按固定顺序计算的 `missing_fields`，由页面提示首个缺失字段；不再使用泛化错误文案，也不伪造字段值。

## 验收与测试

- 对“两个成人带一个孩子，9.10日从北京到成都玩3天，不吃辣，行程不要太赶”提取北京、成都、当年 9 月 10 日、3 人、3 天。
- 不含人数的描述返回 `missing_fields=("travelers",)`，且页面提示“请补充出行人数”。
- 模型响应无效时，规则已提取的字段仍会返回，未识别字段按固定顺序进入 `missing_fields`。
- 既有 API 解析测试与相关完整测试集保持通过。
