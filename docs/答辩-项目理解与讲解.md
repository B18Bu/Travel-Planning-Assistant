# 第一篇 · 项目理解

## 一、这个项目是什么？

一句话：**这是一个「输入旅游需求，自动生成旅行方案」的企业内部工具。**

用户（比如旅行社的规划人员）在网页上填几个信息——从哪出发、去哪、哪天走、几个人、玩几天——系统就会自动帮他查天气、定路线、推荐住宿和吃饭的地方，最终生成一份**可以核验的行程单**（Markdown 文档）。

它和普通的"AI 聊天生成攻略"最大的区别是：**不靠大模型瞎编，而是调用真实地图、真实天气数据，把每一条信息都标出来源**，让建议"看得见、查得清、坏不了"。

## 二、它解决了什么问题？

传统做旅游规划很痛苦：

- 查天气要开一个网站，查路线开另一个，订酒店再开一个，信息散落各处；
- AI 直接生成的行程**经常编造**（虚构的餐厅、过时的价格），用户无法判断真假；
- 出行的日期、人数、预算变了，方案要重做。

这个项目把以上环节整合成一个流水线：天气 → 路线 → 住宿 → 餐饮 → 汇总，每步都调用真实数据源，**结果可追溯、可降级、不编造**。

## 三、它有哪些功能模块？

| 功能 | 做什么 | 数据来源 |
| --- | --- | --- |
| 行程规划 | 生成含天气、路线、住宿、餐饮的完整行程 | 和风天气（天气）、高德地图（地点/路线/POI） |
| 攻略查询 | 在自建的"攻略知识库"里搜索某地攻略，可让大模型生成完整回答 | 本地上传的 PDF/DOCX 攻略文档 |
| 门票查询 | 查询景区门票信息（当前为筹备态，默认关闭） | 飞猪 FlyAI 开放平台 |
| 酒店推荐 | 按城市和日期查酒店价格，并用高德地址补充位置 | 飞猪 FlyAI + 高德地图 |
| 数据看板 | 展示攻略内容的好评率统计 | 用户对检索结果的赞/踩反馈 |

## 四、系统整体长什么样？

```
浏览器页面（用户操作界面）
      │  提交"从哪里→到哪里→哪天→几人"
      ▼
后端服务（FastAPI，负责所有逻辑判断）
      │  按固定顺序依次执行 5 个专业 Agent
      ▼
 ①天气 → ②路线 → ③住宿 → ④餐饮 → ⑤汇总
      │
      ▼
生成一份结构化行程（计算机可读的 JSON 数据）
      │
      ▼
转成适合阅读的 Markdown 文档，渲染到页面上
```

- **前端**：纯静态网页（HTML + JavaScript），负责收集输入、展示结果。
- **后端**：Python 的 FastAPI 框架，负责校验、调用外部服务、组织数据、生成文档。
- **外部数据**：和风天气（天气预报）、高德地图（地点定位、路线、周边店铺）。

## 五、三条最重要的设计原则

1. **不编造事实。** 系统里的天气、景点、餐厅都来自真实 API，调不到就明确标注"暂不可用 / 待核验"，绝不用模型补一个假的。
2. **出了问题能"降级"而不是"崩溃"。** 比如天气接口挂了，行程照样生成，但会明确提示"天气数据暂不可用，请出行前核验"。每个模块都有独立的"安全网"。
3. **全程可追溯。** 每条数据都记录"从哪来的、什么时候拿到的、是实时的还是缓存的"，页面上有"待核验事项"和"来源与更新时间"专栏。

## 六、当前状态

- 属于 **MVP（最小可行产品 / 首个可运行版本）**：提供建议与核验提示，**不涉及预订、支付、下单**。
- 门票、酒店是**默认关闭的只读筹备入口**，需要配置密钥和开关才会开启。
- 已用 7 份真实攻略文档做过检索质量评估，四项指标中"忠实度（回答不编造的程度）"达到 **0.948**。

# 第二篇 · 精讲详讲

> 这一篇逐模块讲清楚：功能怎么用、代码怎么组织、为什么这么设计。按照「从用户点击到最后出结果」的顺序讲。

## 第 1 章 项目背景：为什么做这个项目

### 1.1 行业痛点

旅游规划（尤其是企业内部帮客户做方案）长期存在几个问题：

1. **信息分散**：天气、路线、住宿、餐饮分散在不同网站/平台，人工汇总耗时；
2. **AI 生成不可信**：通用大模型生成的行程经常出现不存在的餐厅、过时的票价、错误的位置；
3. **数据无法核验**：传统方案给不出"这条信息出自哪里"；
4. **参数一变全重来**：出行日期、人数、预算变化后，方案难以复用。

### 1.2 项目目标

做一个**只读、可追溯、可降级**的行程建议服务。核心不是"生成得像"，而是：

- 事实有来源（每条信息标注出处）；
- 建议可解释（为什么推荐这个区域、这个时间）；
- 系统可降级（外部服务挂了也能给出最小可用方案）；
- 行为可审计（每次请求都有追踪标识，方便排查）。

### 1.3 项目"宪法"

项目根目录下 `docs/项目宪法.md` 是最高规则，几条硬性约束深刻影响了实现：

- **绝不编造实时交易信息**：不能暗示"这个房有货""这个票价多少钱""一定不会下雨"；
- **禁止字段**：价格、库存、可订状态、评分、排队时长等字段被数据模型直接拒绝（属于"不允许带进系统"的字段）；
- **模型不能成为事实来源**：天气、路线等实时信息必须来自 API，大模型只能做整理、解释、起草这类"判断类"工作；
- **失败必须显式暴露**：任何模块失败都要在最终文档里说明，不允许悄悄掩盖。

> 理解这一点很重要：**这个项目的"气质"是保守、严谨、把安全合规放在第一位**，而不是追求"看起来很智能"。答辩时强调这一点会很有说服力。

### 2.3 请求的完整生命周期

一次"生成行程"的请求，从用户点击到页面显示，经历了这些步骤：

1. 用户在页面填：出发地、目的地、日期、人数、天数、预算、偏好；
2. 前端校验格式（比如日期不能早于今天），发给后端 `/api/travel-plans` 接口；
3. 后端中间件为这次请求生成一个 **请求标识**（`request_id`，一串唯一 ID），贯穿整个过程，出问题好排查；
4. 后端按 Pydantic 合同严格校验参数（地点非空、人数 1—20、日期不早于今天等）；
5. 交给 **编排器**，按固定顺序执行 5 个 Agent；
6. 每个 Agent 调用外部服务拿真实数据，生成自己的结构化结果；
7. **汇总 Agent** 把 5 个结果合并，生成最终 Markdown 文档；
8. 前端收到结果，**净化后**渲染到页面（防恶意代码）。

## 第 3 章 核心功能①：行程规划（重点）

这是项目的心脏。我们详细拆解。

### 3.1 输入的请求长什么样

用户在页面填的信息，最终变成这样一份数据（JSON 格式）：

```json
{
  "origin": "上海",          // 出发地
  "destination": "杭州",      // 目的地
  "departure_date": "2026-09-01",  // 出发日期
  "travelers": 2,            // 人数
  "days": 3,                 // 天数（默认 3 天）
  "budget": 3000,            // 预算（元）
  "preferences": ["亲子", "美食"]  // 偏好标签
}
```

后端会对每一项做严格校验（Pydantic 自动完成）：

- 地点：去除首尾空格，非空；
- 日期：不能早于今天；
- 人数：1 到 20；
- 天数：1 到 14（默认 3）；
- 预算：0 到 200000 元；
- 偏好：最多 12 项。

**注意一个细节**：住宿"几晚"不是用户填的，是后端根据天数自动算的（`max(天数-1, 0)`，即 3 天算 2 晚），防止用户填一个和天数对不上的数字。

### 3.2 什么是"数据合同"

这是本项目的一个核心概念。所谓"数据合同"，就是**给每种数据定好标准格式，谁都不能随便改**。

举个例子：每个 Agent 的结果必须长一个固定样子——

```json
{
  "agent": "weather",        // 是哪个 Agent 的结果
  "status": "success",       // 状态（见下文）
  "summary": "已获取目的地天气与活动建议。",  // 一句话总结
  "data": { ... },           // 具体数据
  "sources": [ ... ],        // 数据来源（哪些 API）
  "warnings": [ ... ],       // 给用户的提醒
  "request_id": "...",       // 请求标识
  "trace_id": "..."          // 追踪标识（当前与 request_id 相同）
}
```

这个合同用代码强制约束：

- **未声明的字段会被拒绝**（`extra="forbid"`）：供应商想偷偷塞一个"评分"字段？进不来。
- **状态和数据必须匹配**：状态是"成功"，就必须有完整数据；状态是"失败"，就绝对不能有数据。
- **不可修改**（`frozen`）：数据一旦生成就不能被后面的人改，防止"顺手"篡改。

这就是"强类型数据合同"的意义：**让每个环节传递的数据都是可靠的、可验证的**，从源头防止字段漂移和上游垃圾数据污染。

### 3.3 四种"状态"的含义

每个 Agent 的结果有四种状态，这是理解整个系统容错设计的钥匙：

| 状态 | 含义 | 例子 |
| --- | --- | --- |
| `success`（成功） | 数据齐全 | 天气 3 天预报全部拿到 |
| `partial`（部分成功） | 有数据但缺一部分 | 只有 2 天预报，第 3 天没有 |
| `degraded`（降级） | 数据不可用但给了替代方案 | 天气接口挂了，只返回"目的地+请自行核验" |
| `failed`（失败） | 完全失败 | Agent 执行抛异常 |

**整体的状态**由四个 Agent 的个别状态汇总决定：只要有失败的，整体就是失败；只要有降级/部分的，整体就是降级；全成功才是成功。

### 3.4 五个专业 Agent 各干什么

#### ① 天气 Agent

**做什么**：获取目的地出行期间的逐日天气预报，并给出活动建议。

**过程**：
1. 先把目的地地名（如"杭州"）通过高德 API 变成经纬度坐标（这一步叫**地理编码**，geocode）；
2. 用这个坐标去和风天气查未来每天的天气；
3. 把"天气状况文字"翻译成**风险等级**和**建议**：
   - 预报文字含"暴雨 / 台风 / 强对流"→ 高风险 → 建议"减少户外暴露，当日优先室内文化场所"；
   - 含"高温"→ 建议"防晒补水，避免长时间户外暴晒"；
   - 否则 → 低风险，正常出游。

**关键点**：风险判断是**纯代码规则**（关键词匹配），不是模型判断——因为这种判断要确定、可测试，不该交给可能出错的大模型。

#### ② 路线 Agent

**做什么**：安排每天上午、下午、傍晚去哪些景点，并估算景点之间的驾车时间。

**过程**：
1. 把出发地、目的地都转成坐标，调用高德**驾车路线** API，得到往返的距离和时长估算；
2. 每天按"天气 Agent 给的风险"决定搜什么类型的景点：
   - 正常天气 → 搜索"风景名胜"；
   - 高风险天气 → 优先搜"博物馆 / 美术馆 / 展馆"（室内），并标注"已优先安排室内文化场所"；
3. 在目的地坐标周边 50 公里内搜景点（**附近搜索** API）；
4. 把候选景点按"上午 / 下午 / 傍晚"三个时段各排一个，每个建议玩约 **120 分钟**；
5. 对相邻两个景点，再调用驾车路线 API，估算两景点之间的车程。

**降级处理**：如果某个时段搜不到景点，就把这个时段的字段标记为"缺失"（`missing_fields`），最后在文档里提示"请核验"。**绝不拿候选凑数或编造**。

#### ③ 住宿 Agent

**做什么**：推荐"住在哪个区域"，并给出若干住宿候选（只给位置和筛选建议）。

**过程**：
1. 用高德搜索目的地的"住宿服务"POI（POI = 兴趣点 / 地图上的某个地点，这里指酒店民宿）；
2. 只保留分类确实是"住宿服务"的结果，取前 10 个；
3. 每个候选只保留：名称、地址、位置、类别、标签——**不含价格、评分、可订状态**（这些被禁止）。

**为什么只给位置不给价格？** 因为项目没有接入任何酒店的实时交易接口，给价格就是编造。所以住宿 Agent 只回答"住在哪片区域合适"，把价格核验交给用户。

#### ④ 餐饮 Agent

**做什么**：按每天上午的景区推荐午餐、按傍晚（或下午）景区推荐晚餐。

**过程**：
1. 拿到路线 Agent 排好的每日景区；
2. 午餐：用"上午"时段的景区坐标，在周边 **2 公里** 内搜"餐饮服务"；
3. 晚餐：优先用"傍晚"时段的景区，如果没有傍晚就用"下午"时段的；
4. 从高德返回的店铺标签（tags）里提取"推荐菜品"；如果没有标签，就用地点的分类（比如"川菜馆"）作为菜系兜底；
5. 只保留第一个匹配的候选餐厅。

**亮点**：推荐菜品是**从真实地图数据的标签里提取**的，不是模型编的。

#### ⑤ 汇总 Agent

**做什么**：把上面四个 Agent 的结果合并成一份最终文档。

**规则**：
- 按固定顺序聚合来源（天气→路线→住宿→餐饮），**去重**（同一个 API 来源不重复列）；
- 收集所有 Agent 的警告，汇总成"待核验事项"；
- 汇总所有缺失字段；
- 根据四个 Agent 的状态，确定整体状态；
- 用**纯代码模板**把结构化数据渲染成 Markdown 文档（`# 旅行计划` 开头，含天气、每日路线、住宿、餐饮、待核验、来源、降级说明等章节）。

**关键点**：汇总 Agent **不新增任何事实**——它不能自己去查东西，也不能凭空加内容，只能把前面已经有的数据排版。这保证了"最终文档里的每个事实都能追溯到来源"。

### 3.5 编排器：控制顺序的大脑

编排器（`orchestration/sequential.py`）的作用很朴素但很重要：

1. **强制固定顺序**：先天气 → 再路线 → 再住宿 → 再餐饮 → 最后汇总。路线需要天气的结论，餐饮需要路线的景区，所以顺序不能乱；
2. **单个 Agent 挂了不阻断整体**：每个 Agent 外面包了一层"安全网"（`_safe_agent_call`），如果这个 Agent 抛异常，就把它转成一个 `failed` 结果，然后**继续执行后面的 Agent**，最后汇总时把失败暴露给用户。

> 设计哲学：**不要让一个模块的失败拖垮整个方案**。即使天气挂了，住宿和餐饮还是可以按目的地区域给出建议，只是标注缺失。

## 第 4 章 外部服务接入与容错（重点）

### 4.1 两个外部数据源

| 数据源 | 用途 | 固定域名 | 特点 |
| --- | --- | --- | --- |
| 和风天气 | 逐日天气预报（最多 15 天） | `pb5ctx5qqr.re.qweatherapi.com` | 只读 GET 请求 |
| 高德地图 | 地理编码、驾车路线、文本/周边 POI 搜索 | `restapi.amap.com` | 只读 GET 请求 |

**安全设计**：服务域名是**硬编码固定的**，配置里想改都不允许（改了会报错）。这防止了"被配置指到恶意地址"这类攻击。所有请求都**在服务端**发起，密钥只在后端环境变量里，浏览器永远看不到。

### 4.2 数据来源的三种状态

系统对每条数据都要标注它是什么性质：

| 状态 | 含义 |
| --- | --- |
| `realtime`（实时） | 这次请求刚从上游供应商拿到的最新数据 |
| `cached`（缓存） | 从本机内存缓存里读的，不是最新拉取 |
| `degraded`（降级） | 上游没数据，系统给的替代/空结果 |

同时记录两个时间：
- **获取时间**（`retrieved_at`）：本系统什么时候拿到的；
- **来源更新时间**（`source_updated_at`）：供应商内容本身的更新时间（比如和风天气的 `updateTime`）。供应商没给就不能用获取时间冒充。

> 这套"来源时间语义"保证了：用户在页面上看到的每条数据，都知道它"新不新鲜、实不实时"。

### 4.3 容错三板斧：缓存、重试、熔断

这是项目的工程亮点，答辩值得展开讲。

**① 缓存（Cache）**

外部 API 每次调用都要花钱、要等。所以系统把结果存在内存里一段时间：

| 数据 | 缓存时长 |
| --- | --- |
| 高德地理编码（地名→坐标） | 7 天（地点坐标几乎不变） |
| 和风天气预报 | 30 分钟 |
| 高德驾车路线 | 15 分钟 |
| 高德 POI 搜索 | 1 小时 |

命中缓存就返回 `cached`，并刷新获取时间。

**② 重试（Retry）**

网络总有抖动。对**受控的瞬时错误**（网络超时、HTTP 429 限流、5xx 服务器错误）最多重试 3 次，每次等待时间指数递增（0.05 秒、0.1 秒、0.2 秒）。

**注意**：参数错误、鉴权错误这类"重试也没用"的错误**不重试**，避免浪费。

**③ 熔断（Circuit Breaker）**

如果某个服务**连续失败达到阈值**（默认 3 次），就打开"熔断开关"：接下来一段时间（默认 60 秒）**不再真的去请求这个服务**，直接快速返回"服务暂不可用"。这就像家里的保险丝，防止一个已经出问题的服务被反复打到爆。

等熔断时间过了，放一个"试探请求"（半开状态），成功就恢复正常，失败继续熔断。

> 这套机制的名字叫"熔断器模式"（Circuit Breaker），是大型系统保护自身稳定性的经典做法。答辩时能讲清楚"什么时候重试、什么时候熔断、为什么"，是很加分的点。

### 4.4 降级设计总览

| 场景 | 表现 |
| --- | --- |
| 天气接口挂了 | 天气 Agent 返回降级，路线不再用天气约束，页面提示"天气数据暂不可用，请出行前核验" |
| 恶劣天气 | 天气正常但给出风险提示，路线优先排室内景点 |
| 路线接口挂了 | 路线 Agent 降级，住宿和餐饮仍按目的地区域给出建议 |
| 附近没有餐厅 | 餐饮 Agent 降级，提示"附近餐饮候选需以商家官方信息核验" |
| 某个 Agent 抛异常 | 转成失败，继续执行其他 Agent，最终文档列出失败的模块和原因 |

## 第 5 章 前端：页面与安全渲染

### 5.1 页面结构

前端是**纯静态页面**，由后端直接托管（同一个域名提供 API 和页面），称为"同源"部署。页面是一个**工作台**，左侧是功能导航，右侧是内容区。主要视图：

- **行程规划**：填表生成行程（核心功能）；
- **攻略查询**：在攻略知识库里搜索，可让大模型生成完整回答；
- **门票查询**：查景区门票（筹备态）；
- **酒店推荐**：查酒店价格和位置；
- **文档库**：上传、查看攻略文档；
- **数据看板**：好评率统计。

### 5.2 安全渲染（重点，答辩加分项）

页面渲染 Markdown 内容时，做了**双保险**：

1. 先用 `marked` 库把 Markdown 转成 HTML；
2. 再用 `DOMPurify` 库**净化**这个 HTML——禁止 `script`（脚本）、`style`（样式）、`svg`、`math` 标签，禁止所有 `on*` 事件属性（如 `onclick`）。

这样即使上游数据里藏了恶意代码（XSS 攻击 / 提示注入），也会被过滤掉，**不会在浏览器里执行**。

另外：
- 页面里所有文本都用安全的 DOM 方法（`textContent` / `createElement`）渲染，**不用** `innerHTML` 拼字符串（防注入）；
- 前端只请求相对路径的 API（`/api/...`），**不携带任何密钥**；
- 第三方库（marked、DOMPurify）是**本地缓存的固定版本**，不从网上下载，避免供应链被替换。

## 第 6 章 核心功能②：文档知识库与攻略查询

### 6.1 整体定位

前面讲的"行程规划"是**实时数据驱动的确定性流程**；而"攻略查询"是另一套能力——**把人工写的攻略文档（PDF/DOCX）收录进系统，用户提问时检索相关内容**。这是一套典型的 RAG（检索增强生成）架构：先检索文档片段，再让大模型基于片段生成回答。

它解决了两个问题：
1. **让企业自有攻略素材沉淀为可检索的知识库**（而不是躺在硬盘里）；
2. **让回答有出处**——不是大模型凭空生成，而是基于你上传的文档。

### 6.2 文档的生命周期

一份文档从上传到可用，经历四个状态（页面会显示）：

| 状态 | 含义 |
| --- | --- |
| `pending`（等待处理） | 刚上传，排队中 |
| `processing`（处理中） | 正在解析、切块、向量化 |
| `ready`（已处理） | 处理完成，可被检索 |
| `failed`（处理失败） | 解析失败，不进入检索范围 |

文档入库是**异步后台处理**的：上传接口先收下文件、登记记录，然后放后台任务慢慢处理，页面轮询状态。这样用户上传大文件时不会被卡住。

### 6.3 上传与校验

- 只接受 **PDF** 和 **DOCX** 两种格式；
- 上传时**双重校验**：文件类型（MIME，一种标准的文件类型标识，比如 PDF 文件的标准标识是 `application/pdf`）必须和文件后缀一致，还要校验文件"魔数"（文件开头的一串标志字节，PDF 以 `%PDF-` 开头、DOCX 以特定字节开头），防止伪装成文档的恶意文件；
- 单文件默认不超过 **20MB**，单次批量最多 **10 份**。

### 6.4 文档解析

| 格式 | 工具 | 提取内容 |
| --- | --- | --- |
| PDF | PyMuPDF（本地库） | 每页的文字、内嵌图片 |
| DOCX | python-docx（本地库） | 段落文字（保留章节层级）、表格、内嵌图片 |

**图片怎么处理？** 文档里的图表、插图会被抽出来，交给 **Qwen-VL 大模型做 OCR（图片文字识别）**，把图里的文字也变成可检索的内容。如果某张图识别失败，只跳过这张图，**不阻塞整篇文档入库**（受控降级）。

**PDF 的已知局限**：PyMuPDF 只能提取"可访问的文字"，**扫描件（图片型 PDF）**会得到空白正文。这类内容需要人工核验——这是 README 里明确声明的限制，答辩时可以主动说明。

> 补充背景：代码里还有一个 MinerU（PDF 版面解析服务）的客户端，但当前处理链路**不会调用它**，PDF 始终在本地用 PyMuPDF 解析。MinerU 是给后续"外发云端解析"预留的接入点，未启用。

### 6.5 切块（把长文档切成小块）

整篇攻略太长，不能整体丢给检索。系统把文档切成**小块**（chunk），每块上限 **800 个字符**，相邻块有 **100 字符重叠**（避免一句话被从中间切开丢信息）。

每块都会记录**来源位置**：页码、章节、表格编号、图片编号等。这样检索到某块时，页面能显示"这段内容来自《某攻略》第 5 页"，实现可溯源。

### 6.6 向量化与入库

- **向量化**：用本地运行的 **BGE 中文向量模型**（bge-small-zh-v1.5）把每块文字变成一串几百位的数字（称为"向量"，vector）。含义相近的文字，向量也相近；
- **入库**：把向量存进 **Chroma 向量数据库**（本地持久化存储）。只有处理完成的块（`ready`）才会进入检索范围。

### 6.7 检索：语义 + 关键词双通道

用户搜索时，系统**同时用两种方式**检索，再融合：

| 方式 | 原理 | 优势 |
| --- | --- | --- |
| 语义检索（向量） | 把用户问题也变成向量，找"意思最相近"的文档块 | 用户换个说法也能找到 |
| 关键词检索 | 先识别问题里的城市/省份和意图（路线/美食/景点），再精确匹配关键词 | 地名、专有名词找得准 |

**融合算法（RRF，即"倒排融合"）**：两种结果各自按排名打分，合并取前 N 个。如果问题里带省份（如"贵州"），还会**硬性过滤**到同一省份的文档，避免跨地区串答案。每个结果标注它是怎么被匹配到的：语义 / 关键词 / 两者都是。

### 6.8 大模型生成完整回答

用户点"生成完整回答"后：

1. 后端把检索到的**相关片段**（含每条的来源）和**用户问题**一起组装成提示词；
2. 发给 **DeepSeek 大模型**，让它**只基于这些片段**生成 Markdown 回答；
3. 模型的系统指令明确要求：**只使用片段中的事实、不编造**；缺失/模糊的地方标注"待核验"；最后列出引用来源。

**关键约束**：大模型是"素材整理者"，不是"知识来源"。检索为空时，模型会如实回答"没有找到相关信息"，而不是编一个。

> 这背后体现了项目宪法的一条铁律：**模型不能成为事实来源**，只能做归纳、解释、起草这类"判断类"工作。

### 6.9 查询记录与反馈闭环

- 每次检索会保存一条**查询记录**（问题、检索结果快照、生成的回答）；
- 用户可以在结果下点"有用 / 没用"（赞/踩），评价会写进记录；
- "数据看板"从这些评价聚合出统计：**按来源文档**、**按地区**分别算好评率，还有"知识库内容"与"AI 生成内容"的好评率对比。

这个闭环的意义：**好内容看得见，差内容能定位**，可以反过来优化知识库素材。

### 6.10 质量评估（RAG 评估工具）

项目专门做了一套**可复跑的量化评估工具**（在 `backend/evaluation/` 目录），用 16 道真实攻略问题测试"检索 + 生成"的整体质量，四项指标：

| 指标 | 中文解释 | 得分 |
| --- | --- | --- |
| `faithfulness` 忠实度 | 回答有没有编造（越高越好） | **0.948** |
| `context_recall` 上下文召回率 | 该找到的信息有没有找到 | 0.838 |
| `context_precision` 上下文准确率 | 找到的信息是否都相关、排得靠前 | 0.758 |
| `answer_relevance` 相关性 | 回答是否切题、充分 | **0.920** |

这套评估由 **DeepSeek 大模型当"裁判"** 自动打分，可以反复运行、持续追踪质量变化。答辩时展示"我们不是嘴上说好用，而是有量化评估、有报告"，是很有说服力的工程亮点。

## 第 7 章 核心功能③：门票查询与酒店推荐

### 7.1 共同点：只读、默认关闭、严格边界

门票和酒店这两个功能**共同遵守一个原则**：

- **只读**：只查信息，**不创建订单、不处理支付**；
- **默认关闭**：需要配置密钥和开关才开启，未配置时返回"服务尚未配置"（HTTP 503）；
- **不承诺交易**：绝不显示"可预订 / 库存 / 下单"这类信息；
- **严格密钥**：密钥只在服务端环境变量，不出现在命令行、日志、响应里；
- **未开启时不会创建任何会发外部请求的客户端**——杜绝"配置泄漏导致误调用"的可能。

### 7.2 门票查询

门票查询的定位是"**只读文本检索**"，通过**飞猪 AI 开放平台（FlyAI）**实现。

前端流程：
1. 进入门票页时，前端先请求 `/api/fliggy/status` 检查服务是否可用（不可用则查询按钮禁用）；
2. 用户填"景点关键词、城市、入园日期、人数"，点查询前会弹一个**同意弹窗**，明确告知"只获取门票信息文本摘要，不收集姓名/证件/手机号，不代下单支付"；
3. 用户同意后提交到 `/api/fliggy/tickets/search`。

后端有三种模式（用配置开关 `FLIGGY_TICKET_PROVIDER` 选择）：

| 模式 | 行为 |
| --- | --- |
| `disabled`（关闭，默认） | 不发请求，返回"服务尚未配置"（503） |
| `mock`（模拟） | 返回明确标注的本地演示数据（仅西湖/故宫/黄山有示例商品，附"不代表实时价格"警告） |
| `flyai`（真实） | 调用飞猪 FlyAI 真实接口 |

**FlyAI 调用细节**：后端不是直连 FlyAI 的 HTTP 接口，而是调用官方提供的 `flyai` 命令行工具（CLI）**子进程**去执行查询。**API Key 通过子进程的环境变量注入**（`FLYAI_API_KEY`），绝不出现在命令行参数、日志或异常里。

- 用户没填城市：调用 `ai-search` 做文本检索，返回一段文字摘要；
- 用户填了城市：调用 `search-poi` 按城市 + 关键词查，返回景点门票信息列表。

**为什么价格固定显示"信息暂不可用"？** 因为 FlyAI 文本检索返回的是自然语言摘要，**不是结构化的实时价格/库存数据**。系统有明确规则：**绝不从自然语言文本里去猜价格和库存**（那等于编造）。所以门票页价格一律显示"信息暂不可用"，只展示文本摘要和位置参考。

### 7.3 酒店推荐（两种数据源并列）

酒店功能提供**两种互不混用的模式**：

| 模式 | 名称 | 数据来源 | 适用对象 |
| --- | --- | --- | --- |
| 模式一 | 飞猪 TOP 酒店低价查询（企业模式） | 飞猪开放平台 TOP 接口 | 有飞猪商旅分销资质的部署 |
| 模式二 | FlyAI 酒店 + 高德 POI 并列推荐（个人模式） | FlyAI + 高德地图 | 个人开发者 |

#### 模式一：飞猪 TOP 酒店低价查询

面向**企业/商家**，接口是飞猪开放平台的酒店低价查询（API 编号 56180）：

1. **请求签名**：因为是企业级接口，每个请求都要按飞猪规则做 **MD5 签名**——把请求参数按字母序拼接，加上密钥（AppSecret）算出签名，防止请求被篡改。密钥只用于签名，不进日志、不进响应；
2. **参数注入**：渠道值（`sub_channel`）由**后端注入**，不接受前端传，防止越权；
3. **价格换算**：飞猪返回的价格单位是"**分**"（整数），后端换算成"元"（除以 100），用 Decimal（高精度十进制）避免浮点误差，按价格从低到高排序。

#### 模式二：FlyAI 酒店 + 高德 POI 并列推荐

面向**个人开发者**，这是目前页面实际开放的模式：

1. **两个数据源并行查询**：一边用 FlyAI 查酒店的价格/评分/星级/图片/官方详情，一边用高德搜"住宿服务"的 POI（地址/位置）；
2. **合并匹配**：只对两边**规范化后名称完全相等**的酒店合并展示（价格 + 地址放一起）——匹配前会做统一处理（去掉空格、标点、大小写），但不做模糊匹配（绝不猜）。匹配不上的分开展示，**不补造价格或地址**；
3. **三种匹配状态**（`match_status`）：
   - `matched`（已匹配）：FlyAI 和高德两边都有这条酒店；
   - `flyai_only`（仅 FlyAI）：只有价格侧信息，没有高德位置；
   - `poi_only`（仅高德）：只有地址位置，没有 FlyAI 价格；
4. 每个结果卡片会标注来源标签（FlyAI / 高德 POI / 已匹配），用户一眼能看出信息从哪来。

页面展示细节（安全相关）：
- FlyAI 没返回价格 → 显示"价格暂不可用"，**不显示 0**（0 会被误读为免费）；
- 图片只加载 **HTTPS** 地址，加载失败自动隐藏；
- 官方详情链接新窗口打开，带 `rel="noopener noreferrer"`（防止新打开的页面篡改原页面）；
- 所有供应商字段都用 `textContent` 渲染，**不用** `innerHTML`（防注入）。

### 7.4 错误处理总结

> 补充：HTTP 状态码是网络通信的标准约定——**4xx 开头表示"客户端（请求方）的问题"**，**5xx 开头表示"服务器（服务方）的问题"**。比如 422 = 你填的参数不对；503 = 服务没配置好或暂不可用；502 = 上游服务出错。

| 情况 | 返回码 |
| --- | --- |
| 参数不合法（日期、人数超范围等） | 422 |
| 功能未配置 / 开关关闭 / 缺密钥 | 503 |
| FlyAI 上游受控错误（超时、CLI 失败、解析失败） | 502，只返回受控错误码 + 追踪标识 |
| 其他运行时异常 | 503 |

所有错误**只返回受控的错误码和追踪标识**（`trace_id`），绝不泄露 API 密钥、上游原文或内部堆栈。

## 第 8 章 安全设计（答辩重点）

这个项目把安全当成第一优先级，值得系统讲一遍：

### 8.1 密钥安全
- 所有外部 API 密钥**只在后端环境变量**（`.env` 文件）里；
- 密钥**绝不**提交到 Git、写进代码、出现在日志和响应里；
- 前端永远拿不到密钥（浏览器只访问相对路径）。

### 8.2 输入校验
- 所有接口输入用 Pydantic 做类型、长度、范围校验；
- **未知字段会被拒绝**（不允许带没定义的字段进来），防止攻击者往请求里塞东西。

### 8.3 输出安全
- API 返回**通用错误**，不暴露异常堆栈、内部 URL、上游原始响应；
- 供应商原始字段**不透传**给前端——前端只能看到净化后的字段（名称、地址、坐标等）；
- Markdown 渲染双重净化（marked + DOMPurify），防 XSS。

### 8.4 安全响应头
每个响应都带：
- `X-Content-Type-Options: nosniff`（防止浏览器错误解析内容类型）；
- `X-Frame-Options: DENY`（防止页面被嵌入到别的网站做钓鱼）；
- `Referrer-Policy: strict-origin-when-cross-origin`（控制来源信息泄露）；
- `X-Request-Id`（请求标识，方便排查）。

### 8.5 CORS
只允许配置中明确列出的浏览器来源（默认 `http://localhost:5173`），**不使用**通配符 `*`。

## 第 11 章 已知限制与后续方向（答辩"诚实加分项"）

主动讲已知限制，比被评委问到好得多：

**当前限制：**
- 缓存和熔断是**进程内**的（内存），重启即清空，不支持多实例共享；
- 多日行程的外部调用是**顺序执行**的，没有统一的超时预算；
- 附近 POI 只检查坐标非空，未做经纬度格式校验；
- 生产级的认证、限流、租户隔离、密钥集中管理、监控告警**尚未实现**；
- PDF 扫描件（图片型 PDF）的识别依赖 OCR 能力，复杂版面不能保证完全还原；
- 天气只支持和风 15 天窗口内的日期。

**后续方向：**
- 接入生产级治理：认证、限流、监控、密钥轮换；
- 优化缓存（连接池、淘汰策略、single-flight 防击穿）；
- 为知识库或 OTA 扩展做独立的数据合同和安全审查；
- 在保持非交易边界的前提下，扩展更多业务能力。

## 第 12 章 答辩常见问题速查

**Q1：你的项目用了大模型吗？在哪些地方？**
A：用了。核心行程规划**不强依赖**大模型（天气判断、路线安排、汇总都是确定性代码，保证可靠）；大模型用在三处——① 攻略问答的"完整回答"生成（DeepSeek）；② 攻略文档图表的 OCR 识别（Qwen-VL）；③ RAG 检索质量的自动评估裁判（DeepSeek）。这体现了"模型只用于判断类任务，不用模型做路由/确定性转换"的原则。

**Q2：你的系统和直接问 ChatGPT 有什么区别？**
A：ChatGPT 可能编造景点、价格；我们的系统所有实时信息都来自真实 API，每一条都带来源和获取时间，拿不到就明确降级提示，绝不编造。另外我们做了严格的安全边界（禁止交易字段、密钥保护、输出净化）和可追溯性。

**Q3：什么是"Agent"？你项目里的 Agent 是 AI 吗？**
A：这里的"Agent"指**负责一个领域的处理模块**（天气 Agent、路线 Agent 等），强调职责分离、结构化结果、固定顺序协作。它们**不一定调用大模型**——多数是确定性代码调用真实数据。这和"自主决策的 AI Agent"概念不同，本项目的编排是固定顺序、可控可审计的。

**Q4：如果天气接口挂了怎么办？**
A：天气 Agent 返回"降级"（degraded）状态，路线 Agent 不再依赖天气约束，住宿和餐饮仍按目的地区域生成建议；最终文档明确标注"天气数据暂不可用，请出行前核验"。这就是"降级不崩溃"的设计。

**Q5：你们怎么防止 AI 编造信息？**
A：三重机制：① 数据合同禁止编造字段；② 大模型只能基于检索到的片段回答；③ RAG 评估里"忠实度"指标（0.948）量化监控编造程度。另外汇总 Agent 不新增事实，只能排版已有数据。

**Q6：密钥安全怎么做的？**
A：密钥只在后端 `.env` 环境变量，不提交 Git、不写日志、不进响应；前端永远拿不到；固定服务域名白名单；CORS 白名单；所有错误对外统一，不暴露内部细节。

**Q7：项目现在能上线吗？**
A：作为 MVP 可以本地运行和演示，但生产级治理（认证、限流、监控、密钥集中管理）尚未完成，按项目宪法的发布门禁，**暂未达到面向真实用户的生产发布标准**。当前定位是"受控开发 / 内部验证状态"。

**Q8：为什么要固定顺序执行 Agent，而不是让 AI 自己决定？**
A：固定顺序更**可审计、可测试、可降级**。天气 → 路线 → 住宿 → 餐饮有明确的依赖关系，固定顺序保证了每一步拿到的输入是确定的，出了任何问题都能定位到是哪一步。

**Q9：你们的项目有什么实际成果？**
A：① 完整的可运行系统（前端 + 后端 + 外部服务接入 + 文档知识库）；② 40+ 自动化测试；③ RAG 检索质量评估（忠实度 0.948、相关性 0.920）；④ 清晰的架构文档、项目宪法、运行手册。
