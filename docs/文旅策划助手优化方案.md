# 智能文旅策划助手优化方案

> **适用对象：** 景区、文旅集团、地方文旅局及目的地运营方。
>
> **目标定位：** 将当前「AI 生成 + RAG 知识库 + 反馈看板」的教学型 MVP，升级为可安全上线、可持续运营、内容可信、可审计、可扩展的企业级智能文旅服务平台。
>
> **核心原则：** 先解决安全、可信数据和生产稳定性，再建设 Agent、数字人及商业运营能力。数字人不是独立卖点，Agent 也不是简单的提示词升级；二者必须建立在受控工具、可靠知识、实时数据和人工运营机制之上。

---

## 一、现状评估

### 1.1 当前已具备的能力

依据《文旅策划助手_项目文档.md》，项目已实现以下 MVP 能力：

| 能力域 | 已有能力 |
|---|---|
| 旅行规划 | 输入现居地与目的地，生成交通、景点、美食和 2—3 天行程方案。 |
| 目的地攻略 | 输入地区名，优先从 Word/PDF 知识库检索，未命中时由大模型兜底。 |
| 知识检索 | 支持 Word、文本型 PDF、扫描 PDF 的解析；使用 BGE 向量嵌入与 FAISS 检索。 |
| 内容溯源 | 检索命中可展示来源文档、页码或章节。 |
| 用户反馈 | 支持回答级赞/踩，并按来源类型、地区、来源文档进行基础统计。 |
| 基础工程 | FastAPI 后端、原生 HTML/JavaScript 前端、SQLite、`.env` 配置和离线建库流程。 |

### 1.2 当前阶段的判断

当前设计适合作为演示原型、内部知识问答工具或产品验证版本，但尚不满足面向游客公网开放、面向多个景区/区域运营、承接营销活动或对接交易业务的生产要求。

主要差距集中在以下 8 个方面：

1. **安全与权限缺失：** 无身份认证、租户隔离、权限体系、限流与防刷；存在密钥暴露风险。
2. **内容可信度不足：** 交通、票价、营业时间、天气、景区公告等关键事实没有实时权威数据支撑。
3. **AI 质量不可控：** RAG 仅依赖单一向量阈值和文本拼接，缺乏重排序、事实核验、可回答性判断和评测体系。
4. **数据治理不足：** 知识库文档缺少来源授权、版本、生效期、审核、下架和质量评分机制。
5. **生产可靠性不足：** 缺少重试、熔断、缓存、异步任务、真实进度、容灾、监控与告警。
6. **用户体验不完整：** 缺少日期、预算、同行人群、兴趣、无障碍等关键约束，也无法编辑、保存、比较、分享或导出行程。
7. **运营闭环较弱：** 反馈粒度粗、统计口径不严谨，缺少内容运营后台、质量工单、A/B 实验与成本计量。
8. **扩展能力缺位：** 尚未形成受控的旅行规划 Agent、数字人导游、实时服务连接器、多端服务和企业级开放接口。

## 二、目标架构：从「生成工具」升级为「目的地智能服务平台」

### 2.1 平台总体架构

```text
游客端 / 小程序 / H5 / 大屏 / 数字人终端 / 运营后台
                    │
                    ▼
          API 网关与身份访问层
   登录、SSO、租户、RBAC、限流、WAF、审计、配额
                    │
                    ▼
             文旅智能编排层
需求理解 → 检索 → 实时数据查询 → 行程编排 → 冲突校验
        → 内容生成 → 安全审核 → 结果解释 → 人工转接
                    │
      ┌─────────────┼─────────────┐
      ▼             ▼             ▼
知识与内容中心   实时服务连接器   Agent / 数字人服务
CMS、RAG、审核、 地图、天气、交通、 受控工具、会话记忆、
版权、版本、索引 景区公告、票务、酒店 语音、TTS、形象驱动
      │             │             │
      └─────────────┼─────────────┘
                    ▼
          数据与运营治理中心
PostgreSQL、对象存储、向量库、缓存、事件埋点、数据仓库
模型调用成本、质量评测、反馈工单、监控告警、审计日志
```

### 2.2 关键架构原则

- **事实与生成分层：** 价格、开放时间、交通班次、天气、景区公告等必须来源于实时或已审核数据；大模型负责解释、组合和表达，不得把推测包装成事实。
- **检索与回答分层：** 知识库内容为证据数据，不接受其内部指令；模型仅在证据范围内总结，并对每项关键事实展示来源与更新时间。
- **高风险动作需受控：** 预订、支付、退改、投诉、营销触达等能力必须通过已授权工具执行，具备用户确认、权限校验、幂等键和审计记录。
- **多租户天然隔离：** 景区、文旅集团和区域运营方的数据、知识库、配置、统计、成本和人员权限必须在数据模型和查询层同时隔离。
- **可观测优先：** 每一次回答均可定位到请求、模型版本、Prompt 版本、知识库版本、数据源、工具调用、审核结论和用户反馈。

## 三、当前文档中的 P0 上线阻断项

以下事项必须在任何公网、试点或面向真实游客的上线前完成。

### 3.1 身份、权限与密钥安全

| 现状问题 | 风险 | 优化方案 | 验收标准 |
|---|---|---|---|
| `/api/config` 返回生效配置，包含 API Key；前端设置页还会回填密钥。 | 任意访问者可能直接获取 DeepSeek、Qwen、MinerU 等密钥。 | 删除明文密钥读取和前端回填能力；接口仅返回「是否已配置」及模型名称。密钥写入企业 Secret Manager/KMS 或受限运维后台。 | 未认证或普通用户请求中不包含任何密钥；浏览器、日志、接口响应和错误信息中均不能出现完整密钥。 |
| 全站没有登录、租户、角色与数据范围控制。 | 公网开放后会成为免费 AI 代理，且存在越权访问、刷量和数据泄露。 | 接入企业 SSO/OIDC、手机号或企业微信登录；建立组织—租户—用户—角色—资源的 RBAC 模型。 | 未登录访问核心接口返回 `401`；跨租户访问返回 `403`；权限变更可审计。 |
| CORS 为 `*`，无网关限流和配额。 | 恶意站点可跨域调用，模型成本和资源可被耗尽。 | CORS 仅允许正式域名；网关实施用户、IP、设备、租户四维限流；增加 WAF、验证码、预算配额和异常封禁。 | 非白名单域名无法跨域调用；超过阈值返回 `429`；异常流量可告警与自动封禁。 |

### 3.2 XSS、输入安全与依赖安全

当前前端使用 `innerHTML = marked.parse(...)` 渲染模型与知识库内容，并以字符串拼接写入标题、来源和错误信息。模型输出、原始文档、地区名称或上游异常信息均可能成为 XSS 注入入口。

**优化要求：**

- Markdown 渲染后必须通过 DOMPurify 等白名单工具净化；默认禁止原始 HTML、事件属性、`javascript:` URL、SVG/MathML 等高风险内容。
- 业务字段使用 `textContent` 或自动转义模板；不得拼接未转义 HTML。
- 第三方前端依赖固定版本；使用企业静态资源仓库或 SRI 校验。
- 配置 CSP、HSTS、`X-Content-Type-Options`、`frame-ancestors` 等安全响应头。
- 文件上传（如后续开放）需增加类型白名单、病毒扫描、大小限制、对象存储隔离和异步解析。

**验收标准：** 覆盖 `<script>`、事件属性、恶意 Markdown 链接、SVG、表格、来源字段及错误信息的安全用例均不能执行脚本；安全扫描无高危 DOM XSS。

### 3.3 隐私与数据合规

出发地、目的地、出行日期、同行人群、儿童/老人信息、偏好、生成结果和互动记录可能构成个人信息和用户画像。生产版本需建立：

- 个人信息处理清单、数据流图、数据分级分类和个人信息影响评估（PIPIA）。
- 隐私政策、明示同意、未成年人保护、用户数据导出/更正/删除渠道。
- 最小化采集与可配置留存期限；过期会话和行程自动删除或匿名化。
- 第三方模型、OCR、地图、票务等供应商的数据处理协议、数据存储地域与数据出境评估。
- 日志、审计和分析数据脱敏；禁止记录完整身份证件、支付信息及不必要的精确位置。

### 3.4 关键事实必须接入权威实时数据

当前「最快出行」「票价」「营业时间」「天气适配」大多由模型推断。生产环境必须区分：

| 信息类别 | 推荐数据来源 | 输出规则 |
|---|---|---|
| 景区开放时间、临时闭园、预约规则、活动公告 | 景区官方 CMS/官网/运营接口 | 显示来源与更新时间；无有效数据则提示核实。 |
| 天气、灾害、空气质量 | 合规天气服务与应急公告 | 显示采集时间和预警等级。 |
| 路线、距离、通行时间、停车场 | 地图服务与景区停车系统 | 以实时接口为准，标记预估或实时状态。 |
| 交通班次、票价、余票 | 合规 OTA/交通服务接口 | 不得由模型伪造实时价格或可订状态。 |
| 酒店、门票、套餐库存 | 自有 PMS/票务系统或授权供应商 | 仅展示可验证库存；购买动作必须二次确认。 |

**验收标准：** 关键时效字段的来源覆盖率达到 100%，每条均展示更新时间；上游不可用时明确降级，不输出伪实时信息。

### 3.5 反馈与统计数据正确性

当前示例存在两类问题：

1. 同一 `message_id` 可无限提交赞/踩，取消和切换状态只在前端变化，统计会重复累积。
2. `stats()` 示例在关闭数据库连接后仍调用聚合查询，且多来源回答会把一次反馈重复归因给多个文档。

**优化方案：**

- 建立唯一约束：`(tenant_id, user_id 或 device_id, message_id)`，使用 `UPSERT` 保存最终反馈。
- 提供反馈撤销接口，并以服务端状态为准渲染前端。
- `feedback` 必须关联有效消息；建立外键、幂等键和防刷策略。
- 明确统计口径：回答级、主来源文档级或多触点归因三选一，不混用。
- 所有统计 SQL 在关闭连接前执行，并通过空库、并发、多来源和异常数据测试。

## 四、分阶段建设路线图

### 阶段 0：安全可控的企业试点底座（0—2 个月）

**目标：** 将原型变为可在受控范围试点的服务，优先保证安全、稳定、可审计。

| 建设项 | 关键工作 | 交付物 |
|---|---|---|
| 身份与权限 | 登录、JWT、RBAC、租户与数据范围隔离。 | 用户/组织/角色模型、权限矩阵、审计记录。 |
| 密钥与配置治理 | 移除密钥回显；接入 Secret Manager；区分开发、测试、生产配置。 | 配置中心、密钥轮换规范、脱敏接口。 |
| 应用安全 | CORS 白名单、WAF、限流、输入校验、Markdown 净化、CSP。 | 安全基线、扫描报告、渗透测试整改清单。 |
| 生产部署 | Docker 化、Nginx/Ingress、TLS、健康检查、就绪检查、滚动发布。 | CI/CD 流水线、部署手册、回滚方案。 |
| 数据底座 | SQLite 迁移至 PostgreSQL；对象存储管理文档；Redis 缓存。 | 数据库迁移脚本、备份恢复演练记录。 |
| 可观测性 | 结构化日志、请求 ID、Trace、指标与告警。 | 监控看板、SLO、告警规则、值班机制。 |

**阶段验收指标：**

- 核心接口未经认证访问率为 0；跨租户越权测试全部拦截。
- 生产密钥不出现在前端、日志、响应和代码仓库中。
- 服务可滚动发布和回滚；单实例故障不导致整体中断。
- 建立可量化 SLO，例如月可用性 ≥99.9%、核心接口错误率 <1%。

### 阶段 1：可信目的地知识与可执行行程（2—4 个月）

**目标：** 将「生成旅游文本」提升为「带证据、可核验、可编辑的目的地行程建议」。

| 建设项 | 关键工作 |
|---|---|
| 知识库治理 | 建立内容 CMS：来源、版权/授权、责任人、地区标签、版本、生效期、审核状态、失效下架。 |
| 检索升级 | 地名实体识别、元数据过滤、关键词 + 向量混合召回、重排序（reranker）、证据覆盖度与置信度判定。 |
| 可信回答 | 回答按段落/主张引用来源；低置信度时提示「资料不足」并提供人工渠道，不伪造来源。 |
| 实时服务连接器 | 接入景区公告、天气、地图、停车、票务/预约等权威接口。 |
| 行程工作台 | 支持日期、天数、预算、同行人群、兴趣、无障碍需求；支持编辑、替换、地图展示、冲突提示、收藏和分享。 |
| 异步任务与缓存 | OCR、解析、建库采用队列；热门地区和检索结果按知识库版本缓存；真实进度通过 SSE/WebSocket 推送。 |

**阶段验收指标：**

- 地区错召回率 <1%；关键事实引用覆盖率 ≥95%。
- 知识文档均具备授权、责任人、版本与有效期。
- 可检测日期、营业时间、路线、预算等行程冲突。
- 热门地区缓存命中率目标 ≥40%；用户看到的处理进度与后端真实状态一致。

### 阶段 2：受控旅行规划 Agent（4—6 个月）

**目标：** 在受控工作流中引入 Agent，使系统能够多步骤规划、调用工具、校验结果和恢复失败，而不是单纯追加 Prompt。

#### 4.2.1 Agent 适用范围

优先建设以下 3 类 Agent：

| Agent | 主要任务 | 可调用工具 | 不应直接执行的动作 |
|---|---|---|---|
| 旅行规划 Agent | 收集约束、拆解任务、生成候选行程、协调各工具结果。 | 需求画像、知识检索、地图、天气、景区公告、票务查询。 | 未经确认的预订、支付、退改。 |
| 行程校验 Agent | 校验路线、时间、营业状态、预算、拥挤风险与适配性。 | 地图、实时公告、天气、规则引擎。 | 伪造数据、覆盖人工运营规则。 |
| 内容运营 Agent | 协助发现过期内容、低评分文档、知识缺口，生成审核草稿。 | CMS、质量评测、反馈分析、工单系统。 | 直接发布内容、删除文档、修改运营配置。 |

#### 4.2.2 Agent 运行机制

```text
用户需求
  → 需求解析与风险分级
  → 规划 Agent 生成执行计划
  → 工具调用：知识检索 / 地图 / 天气 / 景区公告 / 票务
  → 行程校验 Agent：时间、路线、预算、风险校验
  → 内容生成：证据内总结 + 来源展示
  → 安全审核与置信度判断
  → 返回建议 / 低置信度降级 / 转人工
```

**Agent 建设约束：**

- 每个工具使用明确 JSON Schema，输入、输出、权限、超时、调用预算与审计字段必须固定。
- 使用状态机管理任务：`pending → planning → tool_calling → validating → completed / degraded / escalated`。
- 工具调用必须具备超时、指数退避、熔断、幂等与结果缓存。
- 长任务提供取消能力；用户取消后不再继续无价值调用。
- 会话记忆仅保存用户明确授权且确有价值的偏好；不得把临时敏感信息作为长期记忆。
- 对预订、支付、投诉、营销触达等外部动作强制弹窗确认，并保留审计记录。

**阶段验收指标：**

- 每次 Agent 任务可追溯执行步骤、工具调用、版本和失败原因。
- 工具参数 Schema 校验率 100%；失败可自动降级或转人工。
- 多轮偏好继承在评测集上达到设定准确率，例如 ≥90%。
- Agent 不会在没有用户确认的情况下执行交易或对外动作。

### 阶段 3：数字人导游与多模态服务（6—9 个月）

**目标：** 将经过验证的知识和 Agent 能力包装为数字导游，用于官网/H5、小程序、游客中心大屏、展厅、景区服务终端和直播场景。

#### 4.3.1 数字人优先场景

| 场景 | 价值 | 推荐形态 |
|---|---|---|
| 游客中心迎宾 | 快速介绍景区、活动、服务设施和预约入口。 | 大屏数字人 + 快捷问题。 |
| 景点讲解 | 讲解文化故事、路线背景和注意事项。 | 地理围栏触发的音频/视频讲解。 |
| 智能问答 | 回答营业时间、交通、餐饮、无障碍、母婴室、停车等常见问题。 | 语音对话 + 文本卡片 + 来源链接。 |
| 行程陪伴 | 基于已生成行程提示下一站、天气变化和服务提醒。 | 小程序语音助手，不必优先建设高成本 3D 形象。 |
| 线上营销 | 直播预热、活动宣发、虚拟讲解。 | 预设脚本优先，实时问答需接入审核。 |

#### 4.3.2 数字人技术与合规要求

- **解耦架构：** 文本回答、TTS、ASR、形象渲染、口型驱动、播放控制独立；任一供应商可替换。
- **知识受控：** 数字人只能调用已审核知识和受控 Agent；不得绕过内容审核直接播报模型原始输出。
- **体验指标：** 语音首包、打断恢复、连续会话、网络降级、字幕、静音模式和无障碍支持。
- **授权合规：** 形象、声音、方言素材、音乐和视频必须留存授权；显著展示「AI 生成/数字人」标识。
- **风险控制：** 涉险、医疗、突发事件、未成年人和投诉问题应中止播报并转人工或展示官方渠道。

**阶段验收指标：**

- 形象与音色授权覆盖率 100%，所有合成内容具备 AI 标识。
- 语音首包时间、打断恢复成功率、问答完成率达到体验目标。
- 高风险问题的安全转介率 100%，所有中止与转接事件可审计。

### 阶段 4：运营闭环与规模化商业能力（9—12 个月）

**目标：** 支持多目的地、多租户、多渠道运营，建立内容质量、成本、线索和转化的闭环。

| 建设项 | 关键工作 |
|---|---|
| 多租户 SaaS | 品牌皮肤、域名、组织、成员、角色、知识库、模型策略、配额和账单隔离。 |
| 内容运营后台 | 内容采集、审核、发布、下架、索引发布、灰度、回滚与质量工单。 |
| 质量评测平台 | 离线黄金集、检索评测集、提示注入集、事实核验集、A/B 实验与线上反馈分析。 |
| 成本与计量 | 按租户/场景统计模型 Token、OCR、存储、检索、语音/形象等成本，支持预算和成本熔断。 |
| 渠道与交易 | 对接官网、小程序、OTA、票务、酒店、旅行社和 CRM；建立线索、预订、复购归因。 |
| 运营分析 | 将回答质量、内容消费、咨询、线索、预订、投诉和复购关联，输出目的地 ROI 报告。 |

## 五、数据、知识库与 RAG 优化方案

### 5.1 知识库内容生命周期

```text
内容采集 → 授权校验 → 结构化抽取 → 人工审核 → 发布
    → 索引构建 → 灰度检索 → 质量监控 → 更新 / 下架 / 归档
```

每份知识文档至少应包含：

| 元数据 | 说明 |
|---|---|
| `tenant_id` / `destination_id` | 所属运营主体和目的地，用于隔离与过滤。 |
| `source_type` | 官方公告、运营手册、合作商资料、UGC、第三方授权数据等。 |
| `copyright_status` / `license_proof` | 版权及授权信息。 |
| `owner` / `reviewer` | 内容责任人和审核人。 |
| `version` / `published_at` / `expires_at` | 版本、生效与失效时间。 |
| `content_category` | 景点、餐饮、住宿、活动、交通、服务设施、应急等。 |
| `risk_level` | 普通、时效敏感、高风险信息。 |
| `quality_score` | 基于完整度、时效、反馈和人工审核的质量评分。 |

### 5.2 检索与生成策略

建议由当前的「向量相似度阈值 + 直接拼接」升级为：

```text
输入规范化
  → 地名 / 日期 / 人群 / 预算 / 意图识别
  → 元数据过滤（租户、目的地、有效期、类别、权限）
  → 关键词 + 向量混合召回
  → Reranker 重排序
  → 证据覆盖与可回答性评估
  → 事实段落生成与细粒度引用
  → 内容安全审核与置信度降级
```

**关键规则：**

- 不可信、过期、无授权、跨租户内容不得进入召回池。
- RAG 上下文中的文本一律视为「数据」，不执行其中任何指令。
- 对交通、价格、营业时间等时效字段优先实时连接器；知识库只作为背景说明。
- 回答不能由证据支持时，明确说明资料不足并提供官方入口或人工客服，而非使用大模型补全为确定事实。

### 5.3 评测指标

| 指标 | 含义 | 建议目标 |
|---|---|---|
| Recall@K | 正确证据是否被召回。 | 结合业务集设定，持续提升。 |
| MRR / nDCG | 正确证据的排序质量。 | 核心目的地达到验收阈值。 |
| 地区错召回率 | 返回非当前目的地内容的比例。 | <1%。 |
| 事实引用覆盖率 | 可验证事实带有来源的比例。 | ≥95%。 |
| 过期内容命中率 | 已失效资料仍被回答引用的比例。 | 接近 0。 |
| 低置信度正确降级率 | 资料不足时未编造且正确引导的比例。 | ≥95%。 |
| 用户任务完成率 | 用户获得并采纳可执行方案的比例。 | 按场景持续优化。 |

## 六、数据治理、合规与审计设计

### 6.1 生产数据存储建议

| 数据类型 | 推荐存储 | 说明 |
|---|---|---|
| 用户、租户、行程、反馈、权限、审核记录 | PostgreSQL | 支持事务、并发、约束、审计与多实例部署。 |
| 原始文档、图片、音视频、导出文件 | 企业对象存储 | 启用加密、版本、生命周期、访问签名和防病毒扫描。 |
| 向量与检索索引 | 向量数据库或版本化索引服务 | 支持分区、过滤、灰度发布、回滚和多副本。 |
| 会话、热点结果、限流计数 | Redis | 设置 TTL，避免将敏感信息长期缓存。 |
| 埋点、调用日志、质量指标 | 日志平台 + 数据仓库 | 用于成本、质量、运营和审计分析。 |

### 6.2 审计事件最小字段

每次智能回答至少记录：

- `request_id`、`trace_id`、`tenant_id`、`user_id`、时间和终端类型；
- 需求摘要及脱敏后的关键约束；
- 模型、Prompt、工作流、工具和知识库版本；
- 检索证据、实时数据来源、更新时间和置信度；
- 内容审核、拒答、降级、人工转接结论；
- 用户反馈、后续编辑、分享、转化等结果事件。

审计日志必须具备访问控制、脱敏、留存策略和防篡改能力。

## 七、生产可靠性与运维方案

### 7.1 外部依赖治理

针对大模型、OCR、语音、地图、天气、票务等外部服务，统一建立服务适配层：

- 连接、读取、整体超时分别设置；不使用单一长超时。
- 对可重试错误采用指数退避和抖动；对业务错误不盲目重试。
- 熔断、并发舱壁、供应商降级和多供应商切换。
- 请求幂等键、调用预算、取消机制和成本熔断。
- OCR、文档解析、建库、批量评测等任务走异步队列。

### 7.2 建议的核心监控指标

| 分类 | 指标 |
|---|---|
| 服务稳定性 | QPS、p50/p95/p99 延迟、错误率、可用性、队列积压、数据库连接池。 |
| AI 质量 | RAG 命中率、低置信度率、引用覆盖率、拒答率、安全拦截率、人工转接率。 |
| 成本 | 每租户 Token、OCR 次数、缓存命中率、单次高质量行程成本、预算消耗。 |
| 知识质量 | 过期文档量、索引版本、错召回、低评分文档、知识缺口。 |
| 数字人体验 | ASR 成功率、语音首包、打断恢复、会话完成率、投诉率。 |
| 业务运营 | 方案生成成功率、编辑率、收藏/分享率、线索率、预订转化率、复购率。 |

### 7.3 测试与发布门禁

上线流水线至少包含：

1. 单元测试、接口契约测试、数据库迁移测试；
2. RAG 回归评测、事实核验集、提示注入红队集和内容安全测试；
3. OCR 文档集测试、前端 E2E 测试、可访问性测试；
4. 依赖漏洞扫描、密钥泄露扫描、SAST/DAST；
5. 并发压测、超时/429/5xx 故障注入和恢复演练；
6. 灰度发布、指标观测、自动回滚策略。

建议核心服务单元测试覆盖率 ≥80%，并对模型、Prompt、索引或实时数据源的每次变更保留离线评测报告。

## 八、产品功能补强清单

### 8.1 游客侧优先功能

- 行程约束：出行日期、天数、预算、人数、儿童/老人、兴趣、饮食禁忌、交通偏好、无障碍需求。
- 行程工作台：按天编辑、拖拽排序、替换景点、预算重算、路线图、冲突提醒。
- 可执行服务：预约提醒、停车导航、排队提醒、天气提醒、临时闭园通知、紧急服务入口。
- 内容沉淀：收藏、分享、导出 PDF/图片、跨端恢复、家庭成员协作。
- 服务转接：低置信度、高风险、投诉和复杂订单问题一键转人工客服。

### 8.2 运营侧优先功能

- 目的地、景区、门店、活动、线路和服务设施的 CMS。
- 内容审核、版权管理、版本发布、定时生效、下架和索引灰度。
- 知识缺口识别：高频未命中问题、低评分答案、过期内容、错召回来源。
- 运营活动配置：节庆、演出、夜游、优惠券、客流预警和临时公告。
- 质量与成本看板：按目的地、渠道、人群、知识版本、模型版本、数字人角色查看效果。

### 8.3 商业化与集成能力

- 面向文旅集团：集团—区域—景区多级组织和统一运营看板。
- 面向景区：官网/H5/小程序/大屏/API 多渠道接入，支持品牌皮肤和白标。
- 面向合作方：票务、酒店、餐饮、旅行社、交通和 CRM 的标准 OpenAPI/Webhook。
- 面向计费：按租户、调用量、功能模块、数字人时长或私有化部署进行套餐与成本核算。

## 十、建议的首期立项范围

为避免项目范围失控，首期企业版建议聚焦以下最小闭环：

1. **一个目标目的地或景区群**：先沉淀官方、可授权、可维护的知识与实时服务数据。
2. **一个核心游客场景**：例如「出发前 1—3 天行程规划」或「在园导览与服务问答」，不要同时覆盖全旅程。
3. **一个受控 Agent 工作流**：需求解析 → 检索/实时查询 → 行程编排 → 规则校验 → 引用回答 → 人工转接。
4. **一个运营后台闭环**：内容审核、过期下架、低评分工单、查询与成本看板。
5. **数字人采用轻量切入**：先在游客中心或小程序使用语音导览/2D 数字讲解员，验证用户需求后再投入高成本 3D 实时数字人。

### 首期成功标准

- 安全、权限、隐私、审计和稳定性达到企业试点要求。
- 关键事实均有官方或实时来源，用户可查看更新时间和证据。
- 目标场景中，用户能够完成「提出需求 → 获取可执行行程 → 编辑/保存 → 使用服务」闭环。
- 运营人员能够从低评分、未命中和过期内容中定位问题，并在后台完成修订与发布。
- Agent 与数字人均处于可控范围：有工具边界、预算、审核、降级和人工接管。

## 十一、结论

现有项目已经具备良好的原型基础：双入口服务、RAG、溯源和反馈机制为后续企业化提供了方向。下一步不应直接堆叠数字人或泛化 Agent，而应优先完成以下顺序：

> **安全合规 → 可信知识与实时数据 → 生产底座 → 可执行行程 → 受控 Agent → 数字人体验 → 多租户运营与商业化。**

按此路线推进后，系统将从「能生成旅行攻略的网页」逐步升级为「面向目的地运营方、可持续提供智能导览、行程规划、内容运营与游客服务的企业级文旅智能平台」。
