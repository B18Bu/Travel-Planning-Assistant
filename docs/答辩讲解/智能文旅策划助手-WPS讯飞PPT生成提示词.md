# 智能文旅策划助手答辩 PPT 生成提示词

> 适用平台：WPS AI、讯飞智文。将下方「总提示词」完整复制到 PPT 生成工具中使用。

## 总提示词

```text
请生成一套用于毕业设计答辩的中文 PPT，项目名称为《智能文旅策划助手》。整体讲解时长控制在 10–15 分钟，生成约 15 页。PPT 面向答辩老师，表达应专业、准确、简约，突出工程设计与项目价值，不要写成旅游宣传册。

【项目定位】
这是一个面向企业内部旅行规划场景的只读式智能文旅行程规划服务。用户填写出发地、目的地、出行日期、人数、天数、预算和偏好后，系统汇聚天气、地图路线、住宿、餐饮与文档知识库信息，生成包含行程、来源、待核验事项和降级说明的结构化建议。项目核心主线是：以强类型数据合同承载多 Agent 编排，以确定性代码保证事实正确，以受控能力增强表达与文档处理，并始终保持只读、非交易的安全边界。

【重要事实边界】
- 当前版本是 MVP，只提供出行建议与核验提示。
- 不接入预订、支付、实时价格、库存、评分、排队、优惠、订单链接等交易能力。
- 天气、路线、住宿和餐饮等事实信息由确定性代码与外部受控 API 获取并校验；LLM 不负责自由生成事实。
- 文档知识库支持 DOCX / PDF 的上传、解析、分块、向量化与可溯源检索。

【项目素材：请直接基于以下内容生成，不要尝试读取 HTML 文件】

一、项目背景与价值
- 企业团建和差旅规划需要同时处理日期、活动区域、天气风险、路线估算、住宿区域和餐饮候选等信息。
- 传统人工规划需要在天气、地图、住宿和攻略等多个 App 或网页之间切换，信息容易遗漏且人工汇总耗时。
- 项目将碎片化信息收敛成“行程建议 + 来源 + 待核验事项 + 降级说明”，帮助用户从“手工拼装信息”转向“核验结构化结果”。
- 业务价值包括：降低规划与沟通成本、让天气风险参与行程安排、展示数据来源与更新时间、沉淀企业历史攻略文档。

二、用户痛点（此部分仅做短标签）
- 信息分散
- 决策成本高
- 时间成本大
- 针对性不足
- 信息可信度低
- 企业协同成本高

三、工程难点（此部分仅做短标签）
- 数据源异构
- 字段漂移
- 来源时间混淆
- 上游服务不稳定
- 状态语义不一致
- LLM 幻觉风险

四、输入、输出与核心功能
- 用户输入：出发地、目的地、出行日期、人数、天数、预算、偏好。
- 输出结果：逐日天气风险、上午 / 下午 / 傍晚景区安排、景区间驾车预估、住宿区域建议、午晚餐候选、来源与更新时间、待核验事项、降级说明。
- 天气模块：调用和风天气逐日预报，根据暴雨、台风、强对流、高温等风险生成出行提醒；高风险天气时优先推荐室内文化场所。
- 路线模块：调用高德地理编码、驾车路线和 POI，按天气风险安排逐日景区；单个景区建议时长约 120 分钟，候选不足时明确展示缺失，不复用或伪造候选。
- 住宿模块：根据推荐活动区域查询住宿服务 POI，只输出位置和筛选建议，不输出价格、评分或预订链接。
- 餐饮模块：上午景区对应午餐，傍晚景区对应晚餐；如无傍晚景区则回退下午景区，查询景区附近 2 km 的餐饮 POI，只展示真实名称和地址。
- 汇总模块：聚合天气、路线、住宿、餐饮结果，去重来源、拼接警告、确定顶层状态，并生成可读的 Markdown 行程。

五、系统架构与多 Agent 编排
- 前端层：同源浏览器页面，提供表单、行程正文、待核验事项、来源信息和知识检索入口。
- API 层：FastAPI 负责请求校验、UUID 请求标识、安全响应头、通用错误和健康检查。
- 编排层：SequentialTravelOrchestrator 按固定顺序执行，流程为：天气 → 路线 → 住宿 → 餐饮 → 汇总。
- Agent 层：WeatherAgent、RouteAgent、LodgingAgent、FoodAgent、SummaryAgent。
- 基础设施层：内存缓存、受控重试、熔断器、DocumentStore、ChromaDB 和本地 BGE Embedding。
- 外部服务：和风天气、高德地图；DeepSeek 仅用于受控表达润色，Qwen-VL 仅用于图表 OCR 辅助。
- 单个 Agent 出现异常时，编排器将其转为受控失败结果，其他 Agent 继续执行；最终文档如实展示降级或失败状态。

六、强类型数据合同与可信状态
- 使用 Pydantic v2 定义请求、来源、Agent 结果和最终文档；通过封闭字段、不可变模型和跨字段校验防止字段漂移与状态混乱。
- Agent 状态包括：success、partial、degraded、failed。
- 顶层状态规则：任一 Agent 为 failed 时顶层为 failed；存在 partial 或 degraded 且没有 failed 时顶层为 degraded；其余为 success。
- 来源状态包括 realtime、cached、degraded。
- retrieved_at 表示本服务本次从上游获取或从缓存读取的时间；source_updated_at 表示供应商真正提供的内容更新时间，二者不能混用。
- request_id 与 trace_id 贯穿单次请求，用于日志关联和问题定位。

七、文档知识库与 RAG
- 支持 DOCX / PDF 上传，入库前校验 MIME 类型、文件后缀、文件签名和大小。
- 文档处理流程：本地提取文本与基础结构 → 重叠分块 → 本地 BGE 向量化 → ChromaDB 持久化。
- 查询使用“语义检索 + 关键词检索 + RRF 融合排序”，并支持城市硬过滤，避免语义相近但目的地不符的检索结果。
- 检索结果可回溯到文档名、页码、章节、表格或图片位置。

八、韧性、安全与质量保障
- 韧性策略：天气、地理编码、驾车路线和 POI 使用不同 TTL 的进程内缓存；连接错误、超时、HTTP 429、HTTP 5xx 最多进行 3 次指数退避重试；连续失败达到阈值后开启熔断并返回受控降级。
- 安全策略：密钥只从后端环境变量读取；供应商域名固定；前端只请求同源 API；不向浏览器暴露供应商原始响应、异常堆栈或密钥。
- 前端安全：Markdown 经过 marked 解析与 DOMPurify 净化，禁止危险标签和事件属性；依赖使用本地 vendor 文件，不从 CDN 加载运行时依赖。
- 质量保障：使用 pytest 与 respx 覆盖模型合同、配置、供应商客户端、缓存、重试、熔断、Agent、编排、API 和前端资源；外部 HTTP 调用全部模拟，不产生真实调用费用。

九、项目亮点与后续规划
- 亮点：强类型数据合同驱动；确定性事实与受控表达分离；四态状态机与来源时间语义；缓存、重试、熔断、降级贯穿；可溯源混合检索 RAG；只读、非交易边界清晰。
- 局限：天气预报窗口有限；多日外部调用当前按顺序执行；认证、限流、租户隔离、集中式密钥、审计和监控等生产化治理仍待补齐；复杂版面与扫描件 OCR 仍需增强。
- 后续方向：请求级总超时预算、single-flight 防缓存击穿、共享缓存、认证与限流、审计监控、表达润色与文档解析能力增强。

【统一视觉规范】
- 背景采用浅暖白或米白色，例如 #F6F4EC、#FFFFFF；页面保持大面积留白。
- 主强调色采用低饱和青绿色，例如 #1E6F66；辅助强调色采用少量暖橙，例如 #C97A2B，仅用于章节编号、页码、重点提示或短色条。
- 页面采用极简编号信息版式：左上角显示章节编号，例如“01 / PROJECT BACKGROUND”；标题下方配一条细短的暖橙色条；正文采用短标题、小色块、细边框和轻量卡片。
- 卡片使用白色或浅色底，圆角小于 10 px，边框细且浅，不要使用厚重阴影。
- 字体使用简洁的中文无衬线字体，如思源黑体、微软雅黑或等效字体；标题加粗，正文保持清晰易读。
- 全套 PPT 保持统一页眉、页码和颜色体系。封面可使用小面积青绿色标签，但不要采用深色满屏背景。
- 不使用深色大面积底图、强渐变、炫光、3D 立体装饰、复杂纹理、无关风景大图、人物插画、密集文字或夸张动画。
- 优先使用简洁流程图、分层架构图、状态图、信息卡片和线性图标。图中中文必须清晰可读。

【内容表达规则】
- 每页只表达 1 个核心结论，正文控制在 3–6 条短要点内。
- 不要逐字堆砌技术文档，不要使用大段说明文字。
```
