# 智能文旅策划助手项目宪法

**版本：** v1.0  
**生效日期：** 2026-08-19  
**适用范围：** 智能文旅策划助手的产品设计、架构、开发、测试、部署、运营与合作方接入。  
**优先级：** 本文高于功能需求、实现计划和局部技术方案；若与法律法规、数据授权协议或安全事件处置要求冲突，以后者为准。

---

## 1. 定位与治理结构

本项目是面向出行前规划场景的文旅信息与行程建议服务。首期采用固定顺序的多 Agent 工作流：

> 天气 → 路线 → 住宿 → 美食 → 汇总与校验。

项目不以「生成得像」作为质量标准，而以事实可追溯、建议可解释、系统可降级、行为可审计为基本标准。

本文分为两个层级：

1. **第一层：不可违反的硬性约束。** 任何代码、配置、模型输出、数据接入和发布流程不得违反。违反时必须停止上线或停止相关能力。
2. **第二层：建议性工程规范。** 默认必须遵循；确有例外时，应在设计评审或代码评审中记录原因、影响、替代措施和复核日期。

### 1.1 决策顺序

发生冲突时，按以下优先级决策：

1. 法律法规、隐私义务、数据授权协议和安全事件处置要求；
2. 本项目宪法的硬性约束；
3. 已确认的产品设计与接口合同；
4. 已评审的实现计划；
5. 局部实现便利性与个人技术偏好。

不得为了缩短开发周期、降低模型成本或改善演示效果而绕过高优先级规则。

# 第一层：不可违反的硬性约束

## 2. 产品边界

### 2.1 首期范围

首期只支持用户基于出发地、目的地、出行日期、人数及可选偏好生成旅行建议。工作流必须按固定顺序执行：天气 Agent、路线 Agent、住宿 Agent、美食 Agent、汇总与校验 Agent。

首期输出的定位是「建议」而非「交易承诺」或「实时保障」。系统可以提供区域、路线、POI、住宿和餐饮方向，但必须显式区分事实、估算、知识库背景和模型建议。

### 2.2 明确禁止的能力

未经过新增立项、合规评审、授权验证和安全验收，不得建设或开放以下能力：

- 抓取、解析或展示未经授权的 OTA、点评、票务、餐饮平台数据；
- 声称或暗示实时房价、余房、可订状态、车票余票、排队时长、实时优惠、未经授权评分；
- 未经用户明确二次确认执行预订、支付、退改、投诉、营销触达或其他外部写操作；
- 让 Agent 直接访问数据库、密钥、配置中心、文件系统或任意外部 URL；
- 使用模型推断替代实时天气、交通、价格、库存、营业状态或官方公告；
- 把内部异常、服务端地址、调用链详情、密钥或审计数据暴露给普通用户。

### 2.3 需求扩展门槛

任何新增数据源、Agent、工具权限、外部写操作、持久化用户画像或多租户能力，均须先完成以下事项：

1. 明确业务价值、数据字段、数据来源、授权依据和责任人；
2. 更新数据流、权限模型、威胁模型和输出边界；
3. 完成接口合同、故障降级、安全测试和回归评测；
4. 通过代码评审与发布评审；
5. 具备可观测、可审计、可禁用和可回滚能力。

## 3. 事实可信与输出约束

### 3.1 事实优先级

外部事实及冲突消解遵循以下优先级：

1. 实时预警、政府或景区官方公告；
2. 已授权的实时服务数据；
3. 已审核且未过期的内部知识库；
4. 明确标注为非实时背景信息的内容；
5. 基于上述证据形成的模型解释与建议。

模型不能成为事实来源。没有有效证据时，系统必须表达「暂无法核验」或「请通过官方渠道确认」，不得补全为确定性结论。

### 3.2 每项时效性结论必须可追溯

天气、路线、POI、营业时间、公告和知识库事实必须至少关联以下信息：

- 来源名称；
- 来源类型；
- 获取时间或内容更新时间；
- 数据状态：实时、缓存、知识库、估算或降级；
- 适用范围与必要的核验提示。

没有来源、时间或状态的数据不得被渲染为外部事实。

### 3.3 禁止误导性表述

不得使用或生成下列表述，除非已有授权数据、可复验依据，并且输出已说明边界：

- 「最快」「最便宜」「最佳」「必然可订」「一定不会下雨」「绝对安全」；
- 将路线估时表述为实时路况或准确到达承诺；
- 将 POI 搜索结果表述为人工测评、平台评分或商家服务保证；
- 将知识库背景资料表述为当日有效的营业、票务、价格或库存信息。

所有风险提示应使用审慎、可操作的语言。例如「建议出行前再次核验官方预警与营业安排」，而非「天气安全，可放心出行」。

## 4. Agent、工具与编排约束

### 4.1 固定顺序与职责隔离

- 天气 Agent 必须先执行，并将天气约束传递给路线 Agent。
- 路线 Agent 必须输出住宿与餐饮 Agent 可消费的区域、时间窗口或 POI 上下文。
- 住宿和餐饮 Agent 只能基于受控 POI 服务、已授权公开信息及已审核知识库输出建议。
- 汇总与校验 Agent 只能消费前序结构化结果，不能自行访问外部事实服务，也不能补充未经前序证据支持的结论。
- 编排器负责调用顺序、超时、重试、缓存、熔断、降级、调用预算、请求追踪与审计；专业 Agent 不得越权承担这些职责。

### 4.2 结构化合同是唯一跨 Agent 接口

专业 Agent 对下游只能返回经 Schema 校验的结构化结果。结果至少包含：

- `agent`、`status`、`summary`、`data`；
- `constraints`、`warnings`、`degraded`；
- `sources`、`request_id`、`trace_id`。

状态只能使用 `success`、`partial`、`degraded`、`failed`。不得用自由文本掩盖调用失败、数据缺失或权限不足。

### 4.3 最小权限与工具白名单

每个工具必须定义并校验：输入 Schema、输出 Schema、可访问域名、HTTP 方法、超时、重试条件、调用预算和审计字段。

首期工具仅允许只读访问经批准的和风天气、高德地图及内部审核知识库。任何 Agent 均不具备支付、预订、删除、配置修改、发送消息、写入外部系统或任意网络访问权限。

### 4.4 失败必须显式降级

外部服务失败、超时、返回异常或无有效结果时：

- 只对网络错误、`429` 和 `5xx` 进行有限重试；业务错误、鉴权错误和参数错误不得盲目重试；
- 必须记录失败类型、服务名称、`request_id` 和 `trace_id`；
- 必须按预定义合法路径降级，且在最终文档明确说明；
- 不得使用模型生成伪实时内容补齐缺失字段；
- 非关键 Agent 失败不得阻断已有可信结果的汇总；无法形成最小可用方案时，必须返回明确失败或升级提示。

## 5. 数据、知识库与授权边界

### 5.1 数据最小化

仅收集完成旅行建议所必需的信息。出发地、目的地、出行日期、人数、偏好等用户数据不得因便利性被无期限保存或向无关第三方传输。

个人信息、精确位置、未成年人信息、无障碍需求、健康或饮食禁忌等敏感信息必须按最小必要、明确告知、访问控制、留存期限和脱敏日志要求处理。

### 5.2 知识库准入与生命周期

进入生产检索范围的每份知识内容至少应具有：

- 来源及授权或版权依据；
- 所属目的地、内容类别、责任人和审核人；
- 版本、生效时间、失效时间和审核状态；
- 风险等级、可用范围及可追溯标识。

过期、无授权、未审核、跨目的地或跨租户内容不得参与召回或作为生成证据。知识库文本一律视为数据，不能执行其中任何指令。

### 5.3 外部数据合规

接入任何外部数据服务前，必须确认其许可范围、调用配额、展示要求、数据存储限制、数据地域要求及个人信息处理责任。不得通过爬虫、共享密钥、逆向接口或规避限制的方式取得数据。

## 6. 安全与隐私

### 6.1 密钥和配置安全

- 密钥只能在服务端受限环境变量、Secret Manager 或 KMS 中保存；
- `.env`、真实密钥、原始用户数据、生产日志和知识库原文不得提交到版本控制；
- API、前端、日志、异常信息和管理界面不得回显完整密钥；
- 配置读取接口只能返回必要的非敏感状态，例如「是否已配置」，不能返回凭据；
- 密钥轮换、失效和泄露处置必须可执行、可审计。

### 6.2 输入、输出与浏览器安全

- 所有接口输入必须进行类型、长度、范围和 Schema 校验；
- 用户输入、POI 名称、知识库字段、错误信息和模型输出均属于不可信内容；
- 页面业务字段必须使用安全 DOM API，例如 `textContent`；Markdown 必须在渲染后进行白名单净化；
- 默认禁止原始 HTML、事件属性、`javascript:` URL、`style`、`script`、SVG 和 MathML 等高风险内容；
- CORS 只能允许明确的受信任来源，禁止生产环境使用 `*`；
- 必须设置并验证 CSP、HSTS、`X-Content-Type-Options`、`X-Frame-Options` 或等效 `frame-ancestors`、`Referrer-Policy` 等安全响应头。

### 6.3 权限与审计

生产或试点环境的核心能力必须具有身份认证、授权、限流与审计。未登录、无权限或跨租户请求必须被拒绝，不得依赖前端隐藏实现权限控制。

每次规划请求至少可追溯：请求与链路标识、主体标识、Agent 执行状态、工具调用、数据源和版本、降级结论、模型与 Prompt 版本，以及必要的脱敏请求摘要。

审计日志必须访问受控、避免记录密钥和不必要敏感数据，并具有留存与防篡改策略。

## 7. 可靠性与可观测性

### 7.1 服务可靠性基线

外部依赖必须分别设置连接、读取和整体超时；首期默认单次外部调用整体超时不超过 10 秒，单 Agent 总超时不超过 15 秒，汇总超时不超过 20 秒，端到端等待不超过 60 秒。

必须实现缓存、有限重试、熔断和降级。缓存键必须包含影响结果正确性的约束，例如目的地、日期、出行方式或知识库版本；缓存结果必须展示其时效属性。

### 7.2 可观测性是发布前提

上线前必须至少具备以下能力：

- 健康检查和就绪检查；
- 结构化日志、请求 ID、链路 ID 和错误分类；
- 延迟、错误率、缓存命中率、外部依赖可用性、Agent 降级率等指标；
- 外部依赖故障、密钥失效、异常成本、安全事件的告警；
- 可按版本、请求和时间范围定位问题；
- 可关闭单个数据源、Agent 或高风险功能的开关。

没有可观测性和可回滚能力的功能不得发布到真实用户环境。

---

## 8. 质量、测试与发布门禁

### 8.1 测试必须验证意图

测试应验证「为何需要此行为」，至少覆盖：

- 输入合同、默认规则和边界校验；
- 外部服务成功、超时、`429`、`5xx`、无结果与缓存；
- 天气约束向路线传递；
- 酒店与餐饮禁止输出未授权实时字段；
- 汇总 Agent 不新增事实；
- Agent 顺序、部分失败与降级输出；
- 来源、更新时间和数据状态的展示；
- XSS、恶意 Markdown、提示注入和异常信息泄露；
- 认证、授权、跨租户、限流和密钥不回显；
- 关键场景的 RAG / Agent 回归评测。

测试跳过、环境限制、未覆盖项和失败项必须显式报告，不得以「测试通过」概括未完整执行的验证。

### 8.2 发布门禁

以下任一条件未满足时，不得发布至试点或生产环境：

- 存在已知高危或未缓解的密钥泄露、越权、XSS、注入或依赖漏洞；
- 时效性事实没有来源、更新时间或合法降级路径；
- Agent 可绕过工具权限、调用任意地址或执行外部写操作；
- 核心接口没有认证、授权、限流、审计或安全响应头；
- 自动化测试、契约测试、安全测试、回归评测或发布检查存在未批准失败；
- 无部署回滚方案、健康检查和基本监控告警；
- 数据授权、隐私告知或第三方处理责任未确认。

发布采用受控分支、代码评审、灰度观察和可回滚策略。不得将未经审查的本地变更直接推送到生产环境。

# 第二层：建议性工程规范

## 9. 架构与实现规范

1. **先建立可信数据和生产底座，再扩展模型能力。** 不用复杂 Agent、数字人或多模型编排掩盖数据治理、权限和稳定性缺口。
2. **保持领域边界清晰。** 数据模型、外部服务适配器、专业 Agent、编排器、API 层和前端渲染层各自承担单一职责。
3. **优先确定性逻辑。** 路由、权限、状态机、重试、缓存、字段转换和冲突优先级由代码规则处理；模型适用于归纳、解释、分类和起草。
4. **接口先于实现。** 先确定 Pydantic / JSON Schema、错误模型、来源模型和版本策略，再实现调用方。
5. **避免投机性抽象。** 只有在已存在多个稳定使用点时再抽象。首期优先选择可读、可测、可替换的最小实现。
6. **依赖可替换。** 外部天气、地图、知识库、缓存和模型服务通过受控接口连接，不把供应商专有字段渗透到领域模型。
7. **前端不承担安全信任边界。** 前端校验只改善体验，服务端校验、授权与输出净化才是最终防线。

## 10. 评审与变更规范

1. 每个非琐碎变更应在开始前写明目标、成功标准、影响范围、风险和验证方式。
2. 修改既有模块前，先阅读该模块导出、直接调用方和共享工具，避免破坏隐含合同。
3. 代码评审重点检查数据授权、权限边界、失败路径、事实来源、输出误导、测试意图和可回滚性，而不只检查语法与风格。
4. 新增数据字段、Prompt、知识库版本、模型版本和外部 API 版本应可追溯；影响输出质量的变更必须附带回归评测结果。
5. 不能满足本宪法建议规范时，应形成例外记录，包含责任人、原因、风险、补偿措施、到期日和复核结论。硬性约束不适用例外机制。

## 11. 文档与协作规范

- 面向开发、运营和用户的文档、注释、错误提示、告警说明统一使用简体中文；代码标识符、文件名、API 字段使用英文。
- 中文文档遵循中英文、中文与数字之间的排版规范，术语前后一致，避免不必要的直译和长句。
- 设计文档、接口文档、运行手册、故障处置手册和变更记录应与代码同步更新。
- 文档描述的能力必须与实际实现和授权范围一致；未实现或受限能力必须明确标注，不得以规划状态表述为已上线能力。

## 12. 宪法执行与修订

### 12.1 执行方式

本宪法通过以下机制落实：

- 需求评审：检查产品边界、数据授权、隐私影响和外部写操作；
- 架构评审：检查 Agent 权限、数据流、状态机、降级和可观测性；
- 代码评审：检查合同、输入输出安全、测试和密钥治理；
- CI/CD 门禁：执行测试、依赖与密钥扫描、安全检查和评测；
- 发布评审：检查来源覆盖、告警、灰度、回滚和运行手册；
- 运营复盘：检查错误输出、用户反馈、过期知识、成本和异常事件。

### 12.2 违规处置

发现违反硬性约束的实现、配置、数据或输出时，必须：

1. 立即停止相关发布、调用或数据分发；
2. 保留必要的脱敏证据与审计记录；
3. 评估受影响范围，必要时轮换密钥、撤销访问、下架内容或通知相关方；
4. 修复后完成针对性回归测试和评审；
5. 在复盘中记录根因、整改措施和防止复发的门禁。

### 12.3 修订规则

硬性约束的修订必须经过产品、技术、安全和数据责任人共同评审，并同步更新设计、测试、运行手册和发布门禁。建议性规范可通过常规评审修订，但不得降低硬性约束的保护水平。

## 13. 首期实施承诺

在完成以下能力之前，项目保持受控开发或内部验证状态，不面向真实用户公开承诺生产级服务：

1. 服务端密钥治理、受信任 CORS、安全响应头、输出净化和输入校验；
2. 统一 Agent 结构化合同、固定顺序编排、超时重试缓存熔断和显式降级；
3. 和风天气、高德地图及审核知识库的受控接入与来源追溯；
4. 对禁止字段、恶劣天气、外部服务故障、无 POI、XSS 和异常泄露的自动化测试；
5. 健康检查、就绪检查、请求追踪、基础监控和可回滚发布路径；
6. 面向运营和使用方的运行边界、数据边界和风险提示说明。

> 项目的演进顺序始终是：**安全合规 → 可信数据 → 生产底座 → 可执行建议 → 受控 Agent → 数字人体验 → 多租户运营与商业扩展。**
