# 智能文旅策划助手 v1 企业级版本讲解

**版本：** v1.0  
**文档定位：** 面向管理层、业务团队、研发、测试、运维与安全合规人员的统一版本说明  
**系统定位：** 企业内部、只读式、可追溯的旅行规划建议服务  
**更新日期：** 2026-08-22

---

## 1. 执行摘要

智能文旅策划助手 v1 面向企业内部的出行规划与文旅服务咨询场景，将**天气预报、地理编码、驾车路线、住宿 POI、景区与餐饮 POI**等外部事实汇聚为一份可阅读、可追溯、可核验的旅行建议。页面返回和展示每日天气提醒、展示时段、景区间驾车预估，以及午餐和晚餐建议。

v1 的核心不是替代专业旅行顾问或在线交易平台，而是建立一条受控的事实处理链路：

1. 用户提交出发地、目的地、出行日期、人数等信息；
2. 系统按固定顺序获取天气、路线、住宿与餐饮事实；
3. 每一类结果都携带来源、获取时间、上游更新时间与数据状态；
4. 系统将结构化结果汇总为 Markdown 行程，并展示待核验事项；
5. 当外部服务异常、无结果或数据不足时，系统显式降级，不伪造实时信息。

> **v1 的业务定位：** 可运行、可测试、可审计的企业内部旅行建议 MVP。它只提供建议与核验提示，不提供预订、支付、价格、库存或任何交易能力。

## 2. 版本定位、适用场景与价值

### 2.1 适用场景

v1 适用于以下企业内部场景：

- 企业行政、会务或员工服务团队，为差旅、团建、考察活动快速形成出行前建议；
- 文旅运营、客服或策划团队，为用户咨询生成包含天气、交通与候选地点的基础方案；
- 研发与产品团队验证“多来源事实汇聚 + 可追溯输出 + 受控降级”的技术基线；
- 交付与运维团队验证外部 API 密钥、服务连通性、健康检查和故障降级机制。

### 2.2 不适用场景

以下能力不属于 v1，不能对外承诺为现有功能：

- 酒店、景区、餐饮、交通或票务的预订、支付、退改；
- 实时价格、库存、余房、可订状态、排队时长、优惠、评分、订单链接；
- OTA 数据抓取、未经授权的第三方平台数据接入；
- 用户登录、SSO、RBAC、多租户隔离、运营后台；
- 用户行程持久化、个人数据治理、生产级审计、告警、WAF、灾备；
- 知识库/RAG、DeepSeek 自动汇总、动态 Agent 路由或多模型决策。

### 2.3 各角色获得的价值

| 角色 | v1 可获得的价值 |
| --- | --- |
| 管理层 | 获得可控的 MVP 基线：外部数据有来源、建议不触碰交易、风险与下一步投入边界明确。 |
| 业务团队 | 在单一页面输入基础出行信息后，快速得到天气、路线、住宿、餐饮候选与待核验清单。 |
| 研发团队 | 获得清晰的分层架构、强类型合同、固定编排、可测服务适配层与降级机制。 |
| 测试团队 | 可围绕输入合同、状态机、来源元数据、上游异常和接口响应开展自动化验证。 |
| 运维团队 | 可通过环境变量、健康检查、就绪检查、请求标识、超时、重试和熔断管理服务运行。 |
| 安全与合规团队 | 密钥不进入浏览器，业务合同拒绝交易字段，上游原始响应与内部异常不直接对客户端暴露。 |

## 3. v1 已交付能力

### 3.1 用户输入与输出

用户可提交：

- 出发地；
- 目的地；
- 出行日期；
- 出行人数；
- 可选：行程天数、预算、偏好。

系统返回：

- `itinerary`：机器可读的权威结构化事实；
- `markdown`：面向用户阅读的行程建议；
- `sources`：来源名称、类型、数据状态和时间；
- `warnings`：风险或待核验提示；
- `degraded_agents`：发生降级的专业模块列表；
- `request_id` / `trace_id`：一次请求的关联标识。

`TravelPlanDocument` 的 `itinerary` 返回逐日天气、天气提醒、展示时段、景区建议时长、景区间驾车预估和午晚餐结构化结果；`markdown` 与同源页面展示这些内容。午餐关联上午景区，晚餐关联傍晚景区，傍晚缺失时回退下午景区，并展示可用餐饮候选的真实名称和地址。

### 3.2 四个专业 Agent 与一个汇总器

| 模块 | 已交付职责 | 关键输出 |
| --- | --- | --- |
| 天气 Agent | 通过高德地理编码获得目的地经纬度，再查询和风天气逐日预报 | 每日天气、天气风险等级、活动约束、天气警告 |
| 路线 Agent | 对出发地和目的地地理编码，调用高德驾车路线；按天气选择风景名胜或高风险室内文化场所，生成上午、下午、傍晚时段 | 距离、预计时长、约 120 分钟景区建议、景区间驾车预估、天气提醒、候选不足降级 |
| 住宿 Agent | 按推荐活动区域搜索高德住宿 POI | 推荐区域、住宿候选位置、筛选建议 |
| 餐饮 Agent | 以上午景区查询午餐，以傍晚景区查询晚餐，傍晚缺失时回退下午景区；使用景区坐标附近餐饮 POI | 每日午晚餐真实名称与地址、无结果日期、筛选建议 |
| 汇总 Agent | 汇集四类结构化结果，去重来源、合并警告并生成 Markdown | `TravelPlanDocument` |

### 3.3 端到端业务流程

```text
用户在同源 Web 页面填写出行信息
        │
        ▼
POST /api/travel-plans
        │
        ▼
FastAPI：输入校验、请求标识、安全响应头
        │
        ▼
顺序编排器（固定顺序）
  1. 天气 → 2. 路线 → 3. 住宿 → 4. 餐饮 → 5. 汇总
        │
        ▼
TravelPlanDocument
  ├─ itinerary：结构化事实
  ├─ markdown：阅读表现层
  ├─ sources：来源与时间
  ├─ warnings：待核验提醒
  └─ degraded_agents：降级模块
        │
        ▼
前端净化 Markdown 后展示结果
```

### 3.4 外部数据来源

| 服务 | 当前用途 | 当前端点 | 使用方式 |
| --- | --- | --- | --- |
| 和风天气 | 逐日天气预报 | `GET /v7/weather/3d` | 使用高德地理编码返回的经纬度作为 `location` 参数；最多返回并处理 3 日预报。 |
| 高德地图 | 地理编码 | `GET /v3/geocode/geo` | 地址转换为标准地点名称、经纬度和行政编码。 |
| 高德地图 | 驾车路线 | `GET /v3/direction/driving` | 输出距离与预计时长，仅作路线估算，不承诺实时路况或到达时间。 |
| 高德地图 | POI 文本搜索 | `GET /v5/place/text` | 搜索住宿服务和餐饮服务 POI，限定区域且禁止跨城扩散。 |
| 高德地图 | 附近 POI 搜索 | `GET /v5/place/around` | 餐饮 Agent 以景区经纬度为中心、使用 `餐饮服务` 关键词和后端固定 2000 米半径查询；仅在坐标字符串非空时调用。 |

常规天气使用 `风景名胜` 查询；高风险天气使用 `博物馆`、`美术馆`、`展馆` 查询，并优先安排室内文化场所，开放时间和预约条件仍需核验。每日安排上午、下午、傍晚 3 个时段，每个景区建议约 120 分钟；候选不足时明确标记缺失并降级，不复用候选。

系统不会将供应商原始响应直接透传给浏览器。POI 仅保留名称、地址、经纬度、规范化类别及内部来源标识。餐饮页面仅展示真实名称和地址，不展示评分、推荐指数或招牌菜。

## 4. 架构与职责边界

### 4.1 总体架构

```text
浏览器（同源静态前端）
  │
  │  相对路径请求 /api/*
  ▼
FastAPI 应用
  ├─ 安全中间件：请求标识与安全响应头
  ├─ API 层：请求校验、统一错误隐藏
  ├─ 顺序编排器：固定执行顺序与 Agent 异常隔离
  ├─ 专业 Agent：天气、路线、住宿、餐饮、汇总
  ├─ 外部服务层：和风天气、高德地图、缓存、重试、熔断
  └─ 静态资源：前端与轮播图片
```

### 4.2 职责边界

| 层级 | 负责事项 | 不负责事项 |
| --- | --- | --- |
| API 层 | 合同校验、调用编排器、返回受控响应 | 直接处理旅行策略、直接调用外部服务、暴露密钥 |
| 外部服务层 | 固定 Host、HTTP 请求映射、超时、缓存、重试、熔断、响应规范化 | 业务策略、行程文案生成 |
| 专业 Agent | 领域规则、结构化结果、来源与降级包装 | 密钥管理、自由网络访问、交易写操作 |
| 顺序编排器 | 天气→路线→住宿→餐饮的固定调用顺序、单 Agent 故障隔离 | 更改已获取事实、动态决定外部工具 |
| 汇总 Agent | 聚合结构化结果、生成 Markdown、来源去重、状态归纳 | 再次查询外部服务、补充无来源事实 |
| 前端 | 表单交互、同源 API 调用、安全展示 | 密钥持有、权限判断、事实校验 |

### 4.3 v1 “多 Agent” 的真实含义

v1 中的“多 Agent”是**职责分离、结构化输入输出和固定顺序编排**，不表示每个 Agent 都由大模型自由决策。

该选择带来以下企业级收益：

- 行为路径固定，容易测试与审计；
- 专业模块失败时能局部降级，避免一次外部故障导致整个服务失效；
- 外部事实与文案汇总分离，降低将推测表述为事实的风险；
- 为后续接入模型汇总、知识库或更多 Agent 保留稳定边界。

## 5. 数据可信、可追溯与降级机制

### 5.1 结构化事实优先

`itinerary` 是系统唯一的机器可读事实载体，`markdown` 只是根据已获取事实生成的阅读表现层。

这意味着：

- 下游系统应消费 `itinerary`，而非从 Markdown 反向提取事实；
- 页面文案不得替代结构化事实、来源和状态；
- 当内容不足时，系统以 `warnings`、`missing_fields` 和 `degraded_agents` 明确告知，而不是补写未经验证的信息。

### 5.2 来源与时间语义

每个来源至少包含以下元数据：

| 字段 | 含义 |
| --- | --- |
| `name` | 来源名称，例如和风天气或高德地图。 |
| `type` | 来源类型，例如天气 API、地图 API 或 POI API。 |
| `data_status` | 本次数据来自实时请求、缓存，还是降级结果。 |
| `retrieved_at` | 本服务获取或读取该数据的时间。 |
| `source_updated_at` | 上游明确提供的内容更新时间；未提供时为 `null`，不伪造。 |

### 5.3 专业 Agent 状态

| 状态 | 业务语义 | 处理方式 |
| --- | --- | --- |
| `success` | 数据完整，可用于当前模块的既定输出 | 正常展示结果与来源。 |
| `partial` | 有可用数据，但覆盖范围不足 | 展示已知内容，并说明缺失字段。 |
| `degraded` | 发生上游异常、无有效候选或能力不足，但仍保留最小可用建议 | 显示降级说明、待核验事项和可用的区域化建议。 |
| `failed` | 本模块无法产生有效数据 | 标明失败与缺失字段；后续模块仍可按受控默认值继续。 |

顶层文档状态为 `success`、`degraded` 或 `failed`：任何专业模块出现 `partial` 或 `degraded` 时，顶层为 `degraded`；出现任意 `failed` 时，顶层为 `failed`。

### 5.4 缓存、重试与熔断

当前已知限制需要单独说明，不能视为已解决：和风天气仅支持 3 日预报窗口；多日外部调用按顺序执行，暂未实现 Route 总 deadline；附近 POI 仅按非空坐标字符串调用，未做本地经纬度格式校验；生产化治理尚未实现；天气日期连续性和来源元数据异常容错仍待加强。

v1 对外部 API 使用以下保护机制：

- **进程内 TTL 缓存**：减少重复调用与延迟；
- **有限重试**：仅针对受控的瞬时错误，最大尝试次数由配置控制；
- **连接、读取与总体超时**：避免外部服务拖慢整条请求链路；
- **服务级熔断**：连续失败达到阈值后快速返回受控结果，保护上游与本服务；
- **局部降级**：某个 Agent 不可用时，其余 Agent 继续执行，汇总器标明影响范围。

> v1 缓存为单进程内存缓存。多实例环境下缓存不共享，进程重启后缓存丢失；这是 v1 的明确边界。

## 6. 安全、合规与业务边界

### 6.1 密钥与供应商访问控制

- `HEWEATHER_API_KEY` 与 `AMAP_API_KEY` 仅由后端环境变量读取；
- 本地真实密钥存放在 `backend/.env`，该文件被 Git 忽略；
- 浏览器只访问同源相对路径，不直接访问外部供应商；
- 供应商 Host 固定为受控 HTTPS 域名，客户端不能通过请求参数覆盖；
- 接口错误不返回密钥、Token、Authorization、上游原始响应体或内部 URL。

### 6.2 前端与接口安全

- CORS 只允许配置的来源，不使用通配符；
- 返回 `X-Content-Type-Options: nosniff`、`X-Frame-Options: DENY`、`Referrer-Policy` 等基础安全响应头；
- Markdown 通过本地 DOMPurify 净化后再进入页面；
- 来源、告警、降级信息以 DOM 文本方式渲染；
- WebP 静态图片显式声明为 `image/webp`，避免在 `nosniff` 策略下被浏览器拒绝渲染。

### 6.3 交易字段禁止规则

系统合同拒绝以下交易或实时商业字段及其扩展：

```text
price、live_price、inventory、availability、bookable、queue、queue_time、
discount、rating、review_score、order_url
```

因此 v1 仅输出候选位置、区域、类别、筛选建议、天气风险和核验提示，不对价格、库存、营业、排队、评分或预订结果作出承诺。

### 6.4 当前安全与治理缺口

v1 已建立最小安全边界，但尚未达到企业生产系统的完整治理水平。生产化治理尚未实现，以下能力需要作为独立需求设计和验收：

- SSO / OIDC、用户身份认证与会话治理；
- RBAC、多租户、数据范围隔离；
- 集中式密钥管理（Secret Manager / KMS）；
- 审计日志、监控、告警、WAF、限流与配额；
- 隐私数据治理、数据保留策略、备份与灾备；
- 生产级 API 网关、发布流水线和漏洞治理。

## 7. API、运行与交付说明

### 7.1 核心接口

| 接口 | 用途 | 验收标准 |
| --- | --- | --- |
| `GET /api/health` | 进程存活检查 | 返回 HTTP 200 与 `{"status":"ok"}`。不验证外部密钥。 |
| `GET /api/ready` | 基础配置就绪检查 | 和风与高德密钥均非空时返回 HTTP 200 与 `{"status":"ready"}`；不等同于已验证供应商网络。 |
| `POST /api/travel-plans` | 生成旅行规划 | 接受合法 JSON 请求，返回 `TravelPlanDocument`。 |

### 7.2 最小请求示例

```json
{
  "origin": "北京",
  "destination": "成都",
  "departure_date": "2026-08-22",
  "travelers": 2,
  "days": 3,
  "preferences": ["美食"]
}
```

关键输入约束：

- `departure_date` 不早于服务端当天；
- `travelers` 为 1—20；
- `days` 为 1—14，默认 3；
- `budget` 为 0—200000 的整数或空值；
- `preferences` 最多 12 项；
- 住宿晚数由服务端按 `max(days - 1, 0)` 计算，客户端不能覆盖。

### 7.3 本地启动与交付环境启动

在仓库根目录、Windows PowerShell 中执行：

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r backend\requirements.txt
Copy-Item backend\.env.example backend\.env

$env:PYTHONPATH = "$PWD\backend"
python -m uvicorn app.main:app --app-dir backend --reload --host 127.0.0.1 --port 8000
```

访问地址：

- 前端页面：`http://127.0.0.1:8000/`
- 存活检查：`http://127.0.0.1:8000/api/health`
- 就绪检查：`http://127.0.0.1:8000/api/ready`

### 7.4 关键配置分类

| 配置类别 | 关键变量 | 用途 |
| --- | --- | --- |
| 必需外部密钥 | `HEWEATHER_API_KEY`、`AMAP_API_KEY` | 调用天气与地图服务。 |
| 外部服务 Host | `HEWEATHER_BASE_URL`、`AMAP_BASE_URL` | 后端受控供应商地址。 |
| 超时与韧性 | `EXTERNAL_*_TIMEOUT_SECONDS`、`EXTERNAL_MAX_ATTEMPTS`、`CIRCUIT_BREAKER_*` | 控制外部调用成本与故障影响。 |
| 缓存 | `WEATHER_CACHE_TTL_SECONDS`、`AMAP_*_CACHE_TTL_SECONDS` | 控制不同事实类型的缓存有效期。 |
| 前端访问控制 | `ALLOWED_ORIGINS` | 控制允许跨域访问的浏览器来源。 |

测试数量和结果随当前工作树变化，以当前完整测试命令实际结果为准。本文不保留未经当前完整测试命令确认的固定通过数量。建议使用以下命令完成验证：

```powershell
$env:PYTHONPATH = "$PWD\backend"
```

## 9. v1 限制、风险提示与演进路线

### 9.1 当前 v1 限制

| 限制 | 影响 | 当前处理方式 |
| --- | --- | --- |
| 和风 3 日预报窗口 | 出行日期超出供应商可返回日期范围时，没有可匹配的逐日天气 | 天气 Agent 明确降级并提示出行前再次核验；窗口限制仍存在。 |
| 单进程内存缓存 | 多实例不共享缓存，重启后缓存丢失 | v1 适用于本地/单实例基线；生产化后替换为受控共享缓存。 |
| 顺序外部调用 | 多日天气、路线、POI 等外部调用按顺序执行，当前暂无 Route 总 deadline | 依赖各次调用自身超时；总请求预算仍待加强。 |
| 附近 POI 坐标校验 | 仅在坐标为非空字符串时调用，未做本地经纬度格式校验 | 保留上游和后续合同校验；本地格式校验待加强。 |
| 天气日期与来源容错 | 天气日期连续性、来源元数据异常尚未有完整容错 | 通过状态、缺失字段和来源信息提示；相关校验待加强。 |
| 外部 API 依赖 | 供应商限流、网络异常或数据缺失可能影响局部建议 | 超时、重试、熔断与局部降级。 |
| 无身份与持久化 | 无法提供用户隔离、历史行程、审计闭环 | v1 仅限受控内部试用；生产化前需补齐身份与数据治理。 |
| 生产化治理未实现 | 尚未提供完整认证、限流、租户隔离、密钥治理、审计、监控和灾备 | 作为 v2 独立需求设计和验收，不能视为当前已解决。 |
| 无生成模型依赖 | Markdown 由确定性汇总模板生成，表达自然度有限 | 保证事实边界；模型汇总需单独评审后接入。 |

### 9.2 推荐演进路线

#### v1.x：增强建议质量，但不突破事实边界

- 接入 DeepSeek 作为**最终汇总表达层**：只接收四个 Agent 的结构化事实，生成 Markdown；失败时回退确定性汇总；不得让模型编排工具或新增事实；
- 引入经审核的企业知识库 / RAG：提供目的地背景与内部服务规则，但关键时效事实仍优先外部实时数据；
- 扩展区域规划、偏好规则和候选筛选；
- 增加配置可见性（仅显示“是否已配置”，绝不回显密钥）。

#### v2：生产化治理与规模能力

- 接入 SSO / OIDC、RBAC 与多租户数据隔离；
- 接入 PostgreSQL、Redis、对象存储和异步任务；
- 建立审计日志、指标、链路追踪、告警、限流、配额与 WAF；
- 对接集中式密钥管理、灰度发布、备份与灾备；
- 建立内容评测、人工审核、反馈闭环与数据治理机制。

> 所有 v1.x 与 v2 能力均需独立完成需求澄清、设计评审、安全评审、测试与验收；本路线图不是自动交付承诺。

## 11. 核心术语

| 术语 | 说明 |
| --- | --- |
| Agent | 在 v1 中是承担单一领域职责的受控模块，不等同于可自由调用工具的大模型。 |
| 编排器 | 固定执行天气、路线、住宿、餐饮与汇总顺序的控制模块。 |
| `itinerary` | 结构化、机器可读的权威事实载体。 |
| `markdown` | 基于结构化结果生成的用户阅读表现层。 |
| 降级 | 外部数据不足或服务异常时，系统保留最小可用建议并显式标示缺失。 |
| 熔断 | 连续外部调用失败后，短时间内快速拒绝继续调用以保护系统与供应商。 |
| `retrieved_at` | 本服务获取或读取数据的时间。 |
| `source_updated_at` | 上游供应商明确提供的数据更新时间。 |
| 同源前端 | 前端静态资源与 API 由同一 FastAPI 服务提供，浏览器不直接持有外部服务密钥。 |

## 12. 结论

智能文旅策划助手 v1 已形成一条可运行、可验证、可降级、可追溯的企业内部旅行建议链路：

- 以固定顺序聚合天气、路线、住宿与餐饮事实；
- 以强类型合同约束输入、状态、来源与最终文档；
- 以服务端密钥、固定 Host、超时、重试、熔断和安全渲染建立最小安全边界；
- 以非交易边界避免在 v1 阶段承担价格、库存、预订和支付风险；
- 以明确的限制和演进路线，为后续模型汇总、知识库和生产治理提供可控基础。

v1 的成功标准不是“覆盖所有文旅能力”，而是证明企业可以在受控事实、透明状态与明确边界下，稳定交付一份可供业务人员使用、可由技术团队维护、可由管理层评估的旅行建议服务。
