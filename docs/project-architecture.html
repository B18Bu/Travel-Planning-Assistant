项目总览

本系统是面向企业内部旅行规划场景的只读式行程建议服务：将天气、地图路线、住宿区域与餐饮 POI 汇聚为可追溯的结构化行程，并在同源前端渲染为包含时段、提醒和午晚餐建议的可核验 Markdown 文档。

当前 MVP 不执行预订、支付或交易。系统只提供建议、候选位置与核验提示，不承诺价格、库存、营业状态、排队或预订结果。

架构层

FastAPI 应用入口（backend/app/main.py）挂载安全中间件、CORS、健康检查与前端静态目录；请求进入 SequentialTravelOrchestrator，按「天气 → 路线 → 住宿 → 餐饮 → 汇总」顺序运行五类专业 Agent；结果汇总为 Pydantic 数据合同 TravelPlanDocument，由同源静态前端渲染净化后的 Markdown。

外部服务

和风天气（逐日预报）与高德地图（地理编码、驾车路线、POI 搜索）。密钥仅存于服务端，供应商使用固定域名；浏览器只访问同源相对路径， 供应商原始字段不会透传到 API 响应。

韧性机制

进程内 TTL 缓存命中返回 data_status=cached；仅对连接错误、超时、HTTP 429 与 5xx 做最多 3 次指数退避重试； 连续失败达到阈值后 CircuitBreaker 打开熔断，窗口结束允许探测恢复；单个 Agent 异常转为受控 failed，汇总器保留其余可用信息。

核心接口

GET /api/health（存活）、GET /api/ready（就绪）、POST /api/travel-plans（行程规划）、 POST /api/documents 与 POST /api/documents/batch（文档库上传）； POST /api/fliggy/tickets/search 为默认关闭的筹备入口。

事实边界：本页面描述当前代码与 README 中实际存在的已实现能力，不包含实时指标、可用性承诺或虚构的运行数据； 规划中尚未实现的能力均在对应章节明确标注。

总体架构

系统采用「浏览器 → FastAPI API 层 → SequentialTravelOrchestrator → 五类专业 Agent → TravelPlanDocument → 前端展示」的单链路主流程；和风天气、高德地图作为外部依赖节点， Pydantic 数据合同与缓存 / 重试 / 熔断作为横切机制。颜色仅作辅助，每个节点均带有可读文本。

文字图例：请求从同源浏览器发出，经 FastAPI API 层 完成 Pydantic 校验、 生成 / 规范化 request_id 与 trace_id，隐藏错误并附加安全响应头；随后 SequentialTravelOrchestrator 按固定顺序依次运行天气、路线、住宿、餐饮四个专业 Agent， 最后由汇总 Agent 聚合四结果、去重来源、拼接警告并确定顶层状态，输出 TravelPlanDocument。 和风天气与高德地图由服务端客户端调用（密钥仅存服务端），Pydantic 数据合同贯穿请求与响应， 缓存 / 重试 / 熔断包裹外部 HTTP 客户端以提升韧性。

旅行规划流程

一次旅行规划请求的端到端顺序流程如下。核心机制是：四个专业 Agent 顺序执行，任一 Agent 抛异常时 仅该结果转为受控 failed，其余信息继续进入汇总，最终仍返回一份完整文档。

流程关键约束：

  • itinerary 是唯一机器可消费的事实载体；markdown 是汇总 Agent 按 itinerary 生成的阅读表现层，不能反向解析为事实。
  • 顶层 status 由专业 Agent 状态汇总决定：存在任意 failed 时顶层为 failed；存在 partial 或 degraded 时顶层为 degraded；否则为 success。
  • 前端只调用同源相对路径 /api/travel-plans，不接触服务端供应商密钥；Markdown 先由 marked.parse 转换、再由 DOMPurify.sanitize 净化，禁止 script / style / svg / math 标签与 on* 属性。

文档处理流程

文档上传与知识检索链路如下：文件在 API 层完成 MIME、后缀与文件签名三重校验后接收（202）或拒绝（422）； 接收文件经本地文本提取、分块、BGE 向量化写入 Chroma，检索阶段融合关键词与向量命中，由知识润色模块受控回答。 MinerU 为规划中能力（当前链路不调用）；Qwen-VL 为受控接入能力，仅用于图表 OCR——文档含图表时在默认处理链路中触发，无 Key 时降级跳过。

文档处理关键约束：

  • 接口：POST /api/documents（单文件，返回 202 + DocumentRecord）；POST /api/documents/batch（multipart，重复 files 字段按顺序提交，默认最多 10 份，DOCUMENT_BATCH_MAX_FILES 可设 1—20）。
  • 校验：只接受 MIME 类型与文件后缀一致、且文件签名有效的 PDF 与 DOCX；外层状态为任一文件被接受 → 202，全部校验失败 → 422，没有接受项且存在合法文件因处理器或存储不可用 → 503。
  • 批处理响应逐项（1-based index）：accepted（附 DocumentRecord）/ rejected / unavailable；rejected / unavailable 绝不回显不可信文件名、文件路径或异常详情。未通过文件不入库、不进后台队列。
  • 提取：PDF 当前始终在本地由 PyMuPDF 提取可访问文本与基础结构，DOCX 用 python-docx；PyMuPDF 不能保证扫描件 OCR、复杂版面、图表或表格的完整还原，此类内容需人工核验。
  • 向量化与存储：本地 BGE embedding 模型（BGE_MODEL_PATH）分块嵌入，写入 Chroma 集合（CHROMA_COLLECTION_NAME=travel_documents）。
  • 检索与润色：关键词检索（keyword_search.py）与向量检索经 knowledge_polish.py 受控润色，经 /api/documents/knowledge-search 提供；这些是已实现组件，但尚未接入旅行主规划链路（POST /api/travel-plans 不调用它们）。
  • MinerU 为规划中 · 后续受控外发解析能力（当前处理链路不会调用它）；Qwen-VL 为受控接入能力，仅用于图表 OCR——文档含图表时在默认处理链路中调用，无 Key 时降级跳过。

熔断与韧性

外部服务访问统一由「缓存 → 重试 → 熔断」横切机制包裹：缓存命中直接返回 data_status=cached， 未命中才访问上游；仅连接错误、超时、HTTP 429 与 5xx 触发最多 3 次总尝试（指数退避）的重试，业务参数错误不盲目重试； 连续失败达到阈值后熔断打开，打开期间拒绝上游调用，窗口结束允许探测，探测成功恢复、失败继续降级。

韧性关键约束：

  • 缓存：进程内 TTL 内存缓存，按来源设置 TTL（天气 1800s · 地理编码 604800s · 驾车路线 900s · POI 3600s）。命中返回 data_status=cached 并刷新 retrieved_at；首次上游请求返回 data_status=realtime；供应商真实更新时间才写 source_updated_at。
  • 重试：仅对连接错误、超时、HTTP 429、HTTP 5xx 做最多 3 次总尝试（EXTERNAL_MAX_ATTEMPTS=3，即 1 次初始 + 至多 2 次重试）的指数退避重试；业务参数错误和其他响应不盲目重试。超时：连接 3s、读 8s、总 10s。
  • 熔断：连续失败达到 CIRCUIT_BREAKER_FAILURE_THRESHOLD=3 后打开，保持 CIRCUIT_BREAKER_OPEN_SECONDS=60；打开期间不访问上游，窗口结束允许探测请求，探测成功恢复、失败继续降级。这是进程内熔断，不是分布式流量治理。
  • Agent 异常：单个 Agent 异常转为受控 failed 结果（含 missing_fields 与受控 error 摘要），其余 Agent 继续，汇总器保留其余可用信息，顶层状态反映失败。
  • 状态语义：data_status 有 realtime / cached / degraded。
