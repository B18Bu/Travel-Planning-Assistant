# 智能文旅策划助手 v1 基线设计

**版本：** v1.0  
**日期：** 2026-08-19  
**状态：** 已设计，待评审后实现  
**依据：** 《项目宪法》、[顺序编排式文旅多 Agent 改造设计](./superpowers/specs/2026-08-18-sequential-travel-agents-design.md)

---

## 1. 目标与成功标准

v1 是一个本地可运行、可测试的受控文旅规划基线。它通过固定顺序的多 Agent 工作流生成旅行建议，并证明以下能力已经成立：

1. 用户提交出发地、目的地、出行日期、人数后，系统完成天气 → 路线 → 住宿 → 美食 → 汇总的固定链路。
2. 外部事实只来自和风天气、高德地图及已审核知识库；每项外部事实均携带来源、更新时间和数据状态。
3. 任一外部数据服务不可用时，系统可返回明确降级的最小可用建议，不伪造实时信息。
4. 最终 Markdown 只基于前序 Agent 的结构化结果生成，不新增未经验证的事实。
5. 前后端输入、输出、密钥和 Markdown 渲染满足 v1 安全基线。

### 1.1 v1 验收标准

| 范畴 | 可验收结果 |
|---|---|
| 主流程 | 有效的四项核心输入可生成默认 3 天 2 晚的文旅建议文档。 |
| 顺序 | 自动化测试证明 Agent 固定按天气、路线、住宿、美食顺序执行。 |
| 可追溯 | 每条天气、路线、POI 或知识库结论至少带来源名称、类型、更新时间与状态。 |
| 降级 | 天气、路线、POI、单 Agent 失败均有预定义且可见的降级说明。 |
| 可信 | 输出中不含无授权实时房价、余房、可订状态、排队、优惠或第三方评分。 |
| 安全 | 前端渲染不执行恶意 Markdown；接口不回显密钥；CORS 不使用通配符。 |
| 工程 | 后端单元、合同与 API 测试全部通过；健康检查、就绪检查和请求标识可用。 |

## 2. 范围

### 2.1 v1 包含

- 单一目的地的出行前旅行建议；
- 必填输入：出发地、目的地、出行日期、人数；
- 可选输入：旅行天数、预算、偏好；未填旅行天数时默认 3 天 2 晚；
- 和风天气：每日预报与恶劣天气活动约束；
- 高德地图：地理编码、驾车路线和文本 POI 搜索；
- 已审核住宿与餐饮知识库的只读检索接口及开发样本；
- 固定顺序的四个专业 Agent 与一个汇总校验 Agent；
- FastAPI API、最小 HTML 表单与安全 Markdown 展示；
- 内存缓存、超时、有限重试、基础熔断接口、显式降级、`request_id` / `trace_id`；
- 自动化测试、运行文档、环境变量示例与密钥泄露检查。

### 2.2 v1 不包含

以下内容不属于 v1；即使实现中发现相关改进机会，也不在本版本顺手扩展：

- 登录、SSO、RBAC、多租户、运营后台与生产级用户管理；
- PostgreSQL、Redis、消息队列、对象存储、异步任务和云端部署；
- 动态 Agent 规划、长期记忆、多模型路由、语音、数字人、多语言；
- 预订、支付、票务、OTA、酒店库存、餐饮排队、优惠、CRM 或营销触达；
- 未授权爬虫、平台评分、实时票价、余票、余房与可订状态；
- PDF 导出、地图可视化、行程编辑、分享、收藏和用户反馈闭环；
- 生产监控平台、告警平台、WAF、完整隐私系统与完整灾备体系。

这些能力必须作为独立需求另行设计、评审和实施。

## 3. 关键设计决策

| 决策 | v1 选择 | 原因 |
|---|---|---|
| 编排模式 | 固定顺序状态机 | 更易审计、测试和降级，避免模型自行决定工具调用。 |
| 外部事实 | 和风天气、高德地图、审核知识库 | 有明确来源与授权边界。 |
| 跨 Agent 通信 | Pydantic 结构化合同 | 防止自由文本污染下游，便于验证来源与状态。 |
| 汇总策略 | 模板 + 规则校验 | 汇总不查询外部服务，不把模型推断伪装为事实。 |
| 缓存 | 进程内内存缓存 | 足以支持本地基线测试；Redis 作为后续替换实现。 |
| 数据持久化 | 默认不持久化用户行程 | 降低 v1 的个人信息与存储治理范围。 |
| 前端 | 静态 HTML / JavaScript | 降低构建复杂度；安全边界仍在服务端与 DOMPurify。 |
| 模型使用 | v1 核心链路不依赖生成模型 | 先验证受控事实链路与文档模板；自然语言解释可作为后续独立能力。 |

> **边界说明：** 「多 Agent」在 v1 中表示职责分离、结构化结果和顺序编排，不意味着每个 Agent 必须调用大模型。天气风险判断、路线约束传递、候选项合并和汇总均优先使用确定性代码。

## 4. 系统上下文与运行流程

```text
浏览器表单
    │ POST /api/travel-plans
    ▼
FastAPI API 层
    │ 输入校验、request_id、响应安全头
    ▼
顺序编排器
    │
    ├─ 1. 天气 Agent ── 和风天气 + 高德地理编码
    │        └─ 输出天气风险与活动约束
    ├─ 2. 路线 Agent ── 高德地理编码 + 路径规划
    │        └─ 消费天气约束，输出每日活动区域
    ├─ 3. 住宿 Agent ── 高德 POI + 审核住宿知识库
    │        └─ 消费每日活动区域，输出住宿区域与候选项
    ├─ 4. 美食 Agent ── 高德 POI + 审核餐饮知识库
    │        └─ 消费每日活动区域，输出每日餐饮候选项
    └─ 5. 汇总校验 Agent ── 规则 + 模板
             └─ 输出 Markdown、来源、警告与降级说明
    ▼
TravelPlanDocument JSON
    ▼
前端 Markdown 渲染 + DOMPurify 净化
```

### 4.1 状态流转

```text
RECEIVED
  → VALIDATING
  → WEATHER_RUNNING
  → ROUTE_RUNNING
  → LODGING_RUNNING
  → FOOD_RUNNING
  → SUMMARIZING
  → COMPLETED

任一专业 Agent：success / partial / degraded / failed
整体结果：success / degraded / failed
```

- 专业 Agent 的降级不会自动中止后续步骤；下游只能使用已知的有效字段或确定性默认区域。
- 天气或路线 Agent 无可用结果时，仍可按目的地生成区域化住宿与餐饮建议，但最终文档必须说明缺失项。
- 汇总阶段只能整合前序结果，不能调用外部服务或生成来源之外的事实。

### 5.1 职责禁止事项

| 模块 | 必须负责 | 不得负责 |
|---|---|---|
| API 层 | 输入校验、响应合同、调用编排器 | 业务推理、直接调用外部服务、暴露配置。 |
| 外部服务层 | 域名白名单、请求映射、超时、缓存、错误分类 | 旅行策略、文档生成。 |

| 编排器 | 顺序、调用预算、重试、熔断、降级、追踪 | 修改专业事实、自由生成文档。 |
| 汇总 Agent | 规则校验、模板渲染、来源合并 | 外部查询、补充事实、掩盖降级。 |
| 前端 | 体验、提交与安全展示 | 权限判断、事实校验、密钥持有。 |

## 6. 数据合同

### 6.1 请求合同

`POST /api/travel-plans`

```json
{
  "origin": "北京",
  "destination": "成都",
  "departure_date": "2026-09-01",
  "travelers": 2,
  "days": 3,
  "budget": 5000,
  "preferences": ["文化体验", "川菜"]
}
```

| 字段 | 类型 | 必填 | 规则 |
|---|---|---:|---|
| `origin` | string | 是 | 去除首尾空白，长度 1—100。 |
| `destination` | string | 是 | 去除首尾空白，长度 1—100。 |
| `departure_date` | date | 是 | 不早于服务端当前日期。 |
| `travelers` | integer | 是 | 1—20。 |
| `days` | integer | 否 | 1—14，默认 3。 |
| `budget` | integer | 否 | 0—200000，仅用于预算层级建议，不承诺价格。 |
| `preferences` | string array | 否 | 最多 12 项，仅作为建议筛选条件。 |

`nights` 为服务端派生字段，值为 `max(days - 1, 0)`，客户端不得自行提交。

### 6.2 来源合同

```json
{
  "name": "和风天气",
  "type": "weather_api",
  "updated_at": "2026-08-19T10:00:00+08:00",
  "url": "https://www.qweather.com/"
}
```

来源必须说明名称、类型与更新时间；若是知识库来源，还应在 `data` 或 `warnings` 中明确其版本和非实时属性。

### 6.3 Agent 结果合同

```json
{
  "agent": "weather",
  "status": "success",
  "summary": "已获取目的地天气与活动建议。",
  "data": {},
  "constraints": ["第 1 天避免长时间户外活动"],
  "sources": [],
  "warnings": [],
  "degraded": false,
  "request_id": "...",
  "trace_id": "..."
}
```

| 字段 | 约束 |
|---|---|
| `status` | 仅允许 `success`、`partial`、`degraded`、`failed`。 |
| `summary` | 面向汇总器的简短已证实结论；不能作为无来源事实的补充渠道。 |
| `data` | 必须满足对应 Agent 的领域字段约束；禁止包含密钥、原始异常、未授权时效字段。 |
| `constraints` | 供下游消费的确定性限制，例如恶劣天气下避免长时间户外活动。 |
| `sources` | 所有外部或知识库事实的来源集合。 |
| `warnings` | 对用户可见的核验提示和风险说明。 |
| `degraded` | 只有使用预定义降级路径时才为 `true`。 |

### 6.4 最终响应合同

```json
{
  "request_id": "...",
  "trace_id": "...",
  "status": "degraded",
  "markdown": "# 文旅策划建议\n...",
  "sources": [],
  "warnings": [],
  "degraded_agents": ["lodging"]
}
```

响应不得包含 API Key、内部堆栈、服务端 URL、原始上游响应或未过滤用户输入。

## 7. 外部数据与降级设计

### 7.1 受控外部服务

| 服务 | 允许用途 | 固定路径或能力 | 不得输出 |
|---|---|---|---|
| 和风天气 | 每日天气预报、风险提示 | 天气预报 API | 绝对安全承诺。 |
| 高德地图 | 地理编码、驾车路径、POI 搜索 | 地理编码、路径规划、文本 POI | 实时票务、停车库存、平台评分、无来源营业信息。 |
| 审核知识库 | 住宿与餐饮背景、适配标签 | 只读、目的地过滤 | 过期或未授权内容，实时价格与库存。 |

外部客户端只允许请求配置中指定的 HTTPS 基础域名，并且仅使用明确的 GET 请求路径与参数 Schema。

### 7.2 超时、重试、缓存与熔断

| 项目 | v1 规则 |
|---|---|
| 连接超时 | 3 秒。 |
| 读取超时 | 8 秒。 |
| 单次外部调用总超时 | 10 秒。 |
| 单 Agent 总超时 | 15 秒。 |
| 汇总超时 | 20 秒。 |
| 端到端最大等待 | 60 秒。 |
| 重试条件 | 仅网络错误、`429`、`5xx`。 |
| 重试次数 | 最多 2 次，指数退避并加入抖动。 |
| 熔断 | 同服务连续失败达阈值时暂停调用 1—5 分钟，直接进入降级。 |
| 地理编码缓存 | 地点标准化结果缓存 7 天。 |
| 天气缓存 | 目的地 + 日期缓存 30 分钟；预警结果可使用更短 TTL。 |
| 路线缓存 | 起终点 + 方式 + 日期缓存 15 分钟。 |
| POI 缓存 | 基础 POI 缓存 1 小时。 |

v1 的内存缓存与熔断状态仅在单个进程内有效。该限制必须记录在运行文档中，不能被表述为生产级高可用能力。

### 7.3 降级矩阵

| 场景 | Agent 结果 | 下游行为 | 最终输出 |
|---|---|---|---|
| 天气服务不可用 | `weather: degraded` | 路线不使用天气约束 | 标注天气数据暂不可用，建议出行前核验。 |
| 恶劣天气 | `weather: success` + 约束 | 路线将每日活动建议标记为受天气调整 | 置顶风险提示，避免长时间户外活动。 |
| 高德路径不可用 | `route: degraded` | 住宿和餐饮按目的地区域执行 | 不输出精确通行时间或路线顺序。 |
| POI 不可用 | `lodging/food: degraded` | 使用审核知识库；无结果时输出筛选条件 | 标记非实时，禁止编造商家。 |
| 知识库无结果 | `partial` 或 `degraded` | 保留区域建议 | 告知用户通过官方或授权平台筛选核验。 |
| 任一专业 Agent 超时 | `degraded` 或 `failed` | 继续执行可依赖的后续步骤 | 列出缺失模块与核验建议。 |
| 汇总校验冲突 | `partial` | 按实时预警、官方规则、实时路线的顺序保留高优先级信息 | 明确展示冲突与替代建议。 |

## 8. 专业 Agent 规则

### 8.1 天气 Agent

**输入：** 目的地、出行日期、旅行天数。  
**依赖：** 高德地理编码、和风天气。  
**输出：** 每日天气、气温、天气风险、装备建议、活动约束、来源与更新时间。

确定性风险规则：当预报文本包含「暴雨」「大雨」「台风」「强对流」时，生成对应日期的「避免长时间户外活动」约束，并追加官方预警核验提示。高温等风险应通过预定义阈值或规则表处理，不由模型主观判断。

### 8.2 路线 Agent

**输入：** 出发地、目的地、日期、人数、天数、预算、天气约束。  
**依赖：** 高德地理编码、路径规划。  
**输出：** 往返路线估算、每日活动区域、时间窗口、天气调整标识、来源与更新时间。

路径时长只能表述为「地图估算」；不得表述为实时路况、最快方案或准确到达承诺。天气约束存在时，输出必须显式标记 `weather_adjusted: true`。

### 8.3 住宿 Agent

**输入：** 人数、住宿晚数、每日活动区域、预算层级、偏好。  
**依赖：** 高德 POI、审核住宿知识库。  
**输出：** 推荐住宿区域、候选 POI、通勤便利性、设施标签、适配人群、来源与更新时间。

禁止字段：价格、实时房价、库存、余房、可订状态、平台评分、订单链接。无候选项时，输出区域、筛选条件及官方或授权平台核验建议。

### 8.4 美食 Agent

**输入：** 每日活动区域、就餐时间、人数、预算层级、饮食偏好。  
**依赖：** 高德 POI、审核餐饮知识库。  
**输出：** 按日和区域组织的餐饮候选项、菜系、特色、位置、适配说明、来源与更新时间。

禁止字段：排队时长、实时优惠、未授权评分、实时营业承诺。无候选项时，输出餐饮区域、菜系方向、筛选条件及核验提示。

### 8.5 汇总与校验 Agent

**输入：** 前 4 个 Agent 的结构化结果和执行状态。  
**依赖：** 仅规则和模板，不调用外部服务。  
**输出：** 最终 Markdown、合并来源、警告、降级模块清单。

必须执行：状态汇总、来源去重、警告收集、降级说明和禁止字段扫描。不得生成前序结果未包含的商家、价格、票务、库存、营业状态或安全承诺。

## 9. API 与前端设计

### 9.1 API

| 方法 | 路径 | 用途 | 响应 |
|---|---|---|---|
| `GET` | `/api/health` | 进程存活检查 | `200` 与 `{ "status": "ok" }`。 |
| `GET` | `/api/ready` | 外部密钥配置就绪检查 | 密钥缺失时 `503`；不返回密钥。 |
| `POST` | `/api/travel-plans` | 创建 v1 文旅规划 | `TravelPlanDocument`。 |

接口统一响应安全头，并返回 `X-Request-Id`。业务错误返回面向用户的中文提示；日志可保留受控错误分类，但响应不得返回上游堆栈或内部详情。

### 9.2 前端

页面只包含一张表单与一个结果区：

- 表单提交前进行基础必填与范围提示；服务端仍是唯一有效校验边界；
- 使用 `fetch` 调用 `/api/travel-plans`；
- Markdown 经 `marked` 解析后，必须由固定版本的 DOMPurify 进行白名单净化；
- 来源、警告与降级说明使用 `createElement` / `textContent` 渲染；
- 不从任何 API 读取或保存密钥；
- 不在 v1 中增加账号、历史记录、收藏、分享或富编辑功能。

## 10. 安全基线

1. `.env` 不入库，`.env.example` 只包含空值和非敏感默认配置。
2. 后端仅从环境变量读取和风天气、高德地图密钥；不提供密钥读取或回填接口。
3. CORS 使用明确白名单；开发默认仅允许 `http://localhost:5173`。
4. 所有 API 输入使用 Pydantic 做类型、长度、范围和日期校验。
5. 每个请求生成或透传 `request_id`，并附加到响应头；`trace_id` 在 v1 复用该值。
6. 返回 `X-Content-Type-Options: nosniff`、`X-Frame-Options: DENY` 和 `Referrer-Policy: strict-origin-when-cross-origin`；生产部署时由反向代理补充并验证 HSTS 与 CSP。
7. 外部客户端捕获超时、传输错误和异常 HTTP 状态，映射为受控服务不可用错误；不向客户端透传原始异常。
8. Markdown 不允许执行脚本、事件属性、危险 URL 或 SVG / MathML 内容。
9. v1 不保存用户行程、偏好或模型上下文；调试日志只保留必要的脱敏字段。

## 12. 交付物与实施顺序

### 12.1 交付物

1. `backend/`：可运行的 FastAPI v1 服务与自动化测试；
2. `frontend/`：最小安全表单与结果展示页面；
3. `.env.example` 与 `.gitignore`：非敏感运行配置和本地数据保护规则；
4. `README.md`：本地运行、测试、外部 API 配置和数据边界说明；
5. 本设计文档及后续逐任务实现计划。

### 12.2 实施顺序

1. 创建安全应用骨架、配置和健康检查；
2. 定义旅行请求、来源、Agent 结果和最终文档合同；
3. 实现缓存、和风天气、高德地图和审核知识库服务；
4. 实现天气、路线、住宿、美食与汇总 Agent；
5. 实现固定顺序编排器、降级策略与 API；
6. 实现最小安全前端；
7. 补齐测试、运行文档、密钥扫描与依赖检查。

每一步仅修改该步骤所需的范围。发现相邻问题时，除非其直接阻断当前步骤，不纳入 v1 变更。

## 13. 已知限制与后续入口

- 内存缓存与熔断不支持多实例共享，服务重启后会清空；
- 未提供生产认证、授权、租户隔离、限流、完整审计存储和告警平台；
- 审核知识库在 v1 只提供接口与样本，不提供内容运营后台；
- 路线、POI 和天气依赖外部服务可用性，输出只能在数据状态允许的边界内表述；
- v1 使用模板输出保证事实约束，不等价于自然语言旅行顾问的完整表达能力。

后续迭代必须以单独的范围说明和设计文档进入，不得将本节限制作为本版本的隐性待办事项。
